# Design

## Context

Desktop 与 Console 分别在 `apps/desktop-webui/src/` 和 `apps/console-webui/src/` 以 TypeScript 拼装 HTML；登录和初次初始化由 `onboarding.ts` 独立渲染，快速配置由 `quick-setup.ts` 承担。文字散落在模板、状态计算、异步动作与异常处理中，一些英文状态同时用于逻辑判断。当前没有语言资源系统，`html lang`、初始加载文字和部分日期格式固定为英文。两端通过各自构建脚本复制静态文件并同步到 Go 内嵌资源；`internal/webapp/server.go` 对 `/setup/browser/` 的模块采用明确白名单。

Desktop 的视图调和逻辑刻意保留 Service iframe 及其祖先，Console 也保留表单与焦点；身份、草稿、请求世代和未知结果分别由现有代码管理。语言改动必须接入这些边界。发布信息的版本正文来自各组件内嵌数据，而非 UI 文案资源。

## Goals / Non-Goals

**Goals:**

- 为两套 UI 提供可离线加载、按当前语言渲染的中英文资源；让新增文案缺漏能在已有构建和测试流程中被发现。
- 在托管入口与独立 CLI Desktop 上以一致规则选择语言，同时不引入新的服务端偏好或账号依赖。
- 切换只改变呈现，保留当前上下文，并通过具体的行为和浏览器测试覆盖动态状态。

**Non-Goals:**

- 翻译用户内容、用户 Service、原始日志、技术标识或已有版本更新日志正文；不改变 Core/CLI 协议、Agent 的回复语言与 Work 内容。
- 建立跨设备账号设置、在线翻译服务或繁体中文资源；不重新设计页面导航和交互。

## Decisions

### 1. 明确资源与数据边界

按稳定语义 ID 管理界面字符串与带参数模板，在两端共享语言选择、格式化和校验规则，各应用的词条可按职责分组。英文与简体中文条目、参数名及必要的复数/数量形式必须相容。`Work`、`Core`、`Service` 等稳定对象使用统一术语表，技术值、操作类型、路由、动作 ID 和数据模型保持不变；显示标签在渲染时映射，不能让程序分支依赖译文。

异步状态与错误需要保存可重新渲染的消息 ID、参数、错误码和安全诊断信息，而不是仅缓存先前语言的英文句子；在现有适配器 `adapter.ts`、`lifecycle.ts`、`files.ts`、Console 的 `onboarding.ts`、`quick-setup.ts`、`model-management.ts` 等位置梳理。用户输入参数仍通过现有转义处理；服务端未知自然语言不能当作可信本地化文案，应显示选定语言的可执行概述，安全原文和关联 ID 如需展示作为诊断数据。服务日志与 Agent、用户生成内容始终保留原文。

不选取整页 DOM 扫描翻译或按英文原句查表：这些做法容易翻译用户内容、漏掉动态状态，并把功能判断耦合到翻译。已有版本更新日志正文是版本化内容，旧 Core 可能只有英文，按返回原文呈现；About、Release notes 等控件仍须本地化。

### 2. 选择与持久化

```text
explicit saved choice for this origin
              |
              v
      supported? -- yes --> selected locale
              |
              no
              v
browser preferred languages in order
  zh-* --> zh-CN  |  en-* --> en  |  otherwise --> en
              |
              v
render UI + html lang + locale formatting
```

只有有效的显式选择持久化；没有选择时按浏览器偏好依序匹配中文或英文，均不匹配则为英文。选择浮层提供“跟随浏览器”、`简体中文`、`English` 并表达当前偏好。默认跟随浏览器；恢复自动模式时清除同源显式选择并按当前浏览器偏好重新匹配，存储不可用时仍在当前页保持自动模式。先采用 `zh-CN`，中文变体统一映射到简体中文；英语统一映射到 `en`。保存位置是非敏感的浏览器本地偏好，同一 origin 的托管工作台、管理与登录共享；独立 CLI Desktop 或其他 IP/端口是不同 origin，不承诺共享。存储不可用时本页仍能切换，重新访问按浏览器语言；不写密码或业务草稿到本地存储。

登录与初始化页增加顶栏语言菜单；登录后的 Desktop 和 Serve 使用现有账号菜单或同等可达的菜单。Desktop 的 Work 页面没有全局账号顶栏，可从现有 Work 更多菜单访问语言；设置页如无该入口则提供等价菜单，避免要求用户先离开当前页面。登录/初始化右上角使用地球图标、“语言”和下箭头的单个轻量按钮；登录后账户下拉与Work更多菜单只显示一行语言入口及当前偏好，设置页使用等价按钮。点击后打开共享的锚定单选浮层，先关闭原菜单，避免两层菜单叠加。浮层白底、细边框、小圆角，选中项右侧勾选；支持方向键、Home/End、Enter/Space、Escape、Tab与外侧关闭，选择后关闭并恢复有效入口焦点。共享偏好和浮层逻辑归属apps/ui-shared/i18n.js，外观归属已有controls.css，经现有复制/嵌入流程交付，无新增服务端偏好API。语言切换立即生效，不应为生效而刷新或导航，现有身份、页面、打开的 Service iframe、未保存的文本/图片/表单草稿以及正在观察的请求均保留；密码只保留在当前内存/输入中，沿用既有清理规则。异步回调使用当前语言呈现，不重新发起业务动作。

### 3. 构建、嵌入与首次绘制

在 `apps/ui-shared/` 提供无运行时外部依赖的语言规则及共享术语，在两端本地构建中编入或复制到各自的浏览器资源目录；按当前 `tsconfig` 的 `rootDir: src` 和原生 ES 模块发布方式选择直接编入或同目录复制，避免浏览器指向仓库路径。两应用的资源清单、`scripts/build-cli.mjs` 的 `desktopInputHash` / `consoleInputHash` 及相关发行输入清单必须纳入共享源和词条。

检查并更新 `internal/webapp/server.go` 中 `/setup/browser/` 的精确资源白名单，使登录和初始化模块的静态依赖均同源可取，同时保持既有 CSP 与路径限制。Core 与 CLI 分别重新嵌入资源，运行时仍只需已有 Go 程序。静态 HTML 的初始加载文案和 `lang` 在脚本加载前或应用初始化阶段处理，避免长期显示相反语言；资源加载失败时保留可理解的恢复方式，不因偏好解析或存储失败使页面不可用。

### 4. 后续新增功能的质量门

构建或测试检查中英文键集合、非空值、参数占位符匹配，检测缺失和额外键；对产品 UI 文案的新增硬编码设置可执行检查并限定必要的技术标识与用户内容例外。将检查接入两 WebUI 常规构建/测试及 `make test` 覆盖的入口，包含故意缺项、缺参数、硬编码的反例测试。检查只能证明资源结构和受检源码的约束，不能证明翻译质量或所有动态文案都被提取；浏览器行为测试和人工核查仍需覆盖主要页面、失败、确认、无障碍名称、窄屏和上下文保留。

## Risks / Trade-offs

- [渲染时缓存旧语言或通过显示字符串决定行为] → 将状态 ID 与显示文案分离，覆盖在途操作后切换语言以及业务状态不变的测试。
- [重新渲染导致草稿丢失或 iframe 重载] → 沿用现有调和和身份边界，用 Service 内输入、聊天图片和表单草稿验证 DOM 连续性。
- [静态依赖遗漏或构建输入 hash 不完整] → 测试登录资源依赖、Core 和 CLI 内嵌结果以及修改共享词条后的输入 hash。
- [中文布局或无障碍名称遗漏] → 在 360px 与桌面视口核查中英文页面；机器检查补充人工文案审阅。
- [运行时未知服务端消息没有翻译] → 使用已知错误码对应的双语概述与恢复，未知情况给通用提示并按现有安全规则保留诊断原文。

## Migration Plan

先建立语言资源及检查，再分批迁移两端界面；全部迁移和相关测试通过后统一构建并同步嵌入资源。旧安装不需要数据迁移：无偏好时按浏览器语言选择。回退到旧版恢复英文界面，残留的非敏感语言偏好不影响旧版业务；不修改已发布制品的身份。
