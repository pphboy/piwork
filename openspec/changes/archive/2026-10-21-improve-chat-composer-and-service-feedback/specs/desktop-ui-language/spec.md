# Spec Delta

## ADDED Requirements

### Requirement: Chat 以一体式圆角容器表达输入焦点

**Identifier:** DUL-COMPOSER-001

Agent 辅助栏、常规 Chat 与 Focus chat SHALL 将多行输入和底部 Model/Thinking 摘要、图片、Input options 及 Send/Stop and send 组织在同一浅色圆角容器中。文本区 SHALL 与容器同底并保持清晰留白；输入聚焦时 SHALL 由外层圆角边界提供至少 2px 的可见轮廓，文本区内部不再叠加直角焦点框。工具栏的文字、图标、主次与等高对齐继续遵守 DUL-WORKSPACE-001，既有多行输入能力与可见高度范围保持。

输入焦点离开文本区后，外层 SHALL 不冒充文本区仍被聚焦；工具栏控件 SHALL 保留各自可见键盘焦点。1440px 与 360px、长模型名及 Stop and send 文案下，输入、必要反馈和操作 SHALL 可达，容器及整页无新增横向溢出，焦点轮廓不被裁切。悬停、普通态及聚焦态使用现有浅色语义令牌，不改变其他表单控件。

视觉和背景读取 SHALL 保持同一 Work/Session 的输入节点、草稿、选区及用户焦点；布局切换继续沿原规则恢复同一 Session，不新增输入上下文。Enter、Shift+Enter、输入法、图片、slash、Response settings、发送/取消与未知结果保护 SHALL 保持既有语义，呈现变化不产生设置写入或 Run。

#### Scenario: 三种 Chat 容器使用同一输入层级
- **WHEN** 用户在 Agent 辅助栏、常规 Chat 或 Focus chat 输入消息
- **THEN** 文本区和底部工具栏属于同一圆角容器，输入位置的外层焦点可辨；工具栏保留原主要动作和轻量设置摘要，文本区没有第二个直角焦点框

#### Scenario: 键盘从输入移到工具栏
- **WHEN** 用户用 Tab/Shift+Tab 在文本区与图片、设置及发送控件间移动
- **THEN** 文本输入的外层轮廓与当前控件焦点分别正确显示，当前目标可辨，聚焦不触发发送或设置保存

#### Scenario: 宽窄屏与长底栏内容
- **WHEN** 视口为 1440px 或 360px，当前模型名很长且主动作显示 Stop and send
- **THEN** 摘要按原规则收缩或换行，输入和所有必要操作可达，边界与焦点未被裁切，页面无新增横向溢出

#### Scenario: 背景更新和布局切换保留输入
- **WHEN** 用户编辑同一 Session 草稿并选择部分文字，后台状态返回或用户切换 Chat 布局
- **THEN** 背景读取保留当前节点、输入、焦点与选区，布局恢复遵守原草稿规则；没有额外 Run、模型设置写入或会话创建

### Requirement: Service 启动与异常反馈绑定具体服务及安全诊断

**Identifier:** DUL-SERVICE-FEEDBACK-001

Desktop SHALL 根据当前有效的 Service 观测状态、启用事实及读取确认状态呈现反馈，Work 的 Degraded 等汇总标签 SHALL 不替代具体 Service 的启动或异常。仅确认 Starting 时显示所属启动任务；Failed SHALL 以明确的服务失败标题、可理解原因和下一步呈现，不能仅显示笼统的 capabilities 提示或继续声明正在启动。Stopped、Disabled、读取失败与未确认各有准确的静态说明。Ready 服务的访问仍遵守现有入口及权限规则，其他服务失败不将其表示为失败。

Service 的安全诊断在可取得时 SHALL 保留并可查看错误码、失败阶段、退出码、修复建议及关联标识；主要说明先服务名称、已确认失败及下一步，技术字段与有界日志归所属详情。缺少阶段时 SHALL 不猜测启动或运行中失败，缺少字段时不伪造诊断；旧字符串错误、空值或不合法字段 SHALL 使用安全且可理解的回退。应用内部具体异常只按实际取得的日志表达，不从进程退出码推断。诊断与日志作为文本显示，沿原权限、脱敏及有界快照规则提供。

单个已确认服务故障的详情入口 SHALL 直接定位该 Work 的原 Service，并提供其日志读取；多个故障 SHALL 显示准确的对象摘要并复用现有管理列表及各对象详情，无 Web 入口的故障也可诊断。关联标识没有已确认 Operation 归属时仅作为诊断文本，不能猜测或跳转到其他操作。查看摘要、打开/关闭详情及读取日志 SHALL 不提交服务控制、应用修复或 Run。

当前服务目录读取中断时 SHALL 保留并标明最后确认事实，显示当前未确认及所属只读恢复入口，停止未确认的启动动效；不能清除已确认错误、伪造空集合或将旧 Starting 当作当前持续进行。Work/身份/对象变化后的旧响应不得改写新目标、清理草稿或抢焦点。已有应用在允许保留的短暂 Starting 与背景读取期间 SHALL 继续沿现有同一 iframe 保护，不为了展示新启动占位重挂应用。启动占位的四格规则遵守 UIL-PENDING-001 的明确例外。

#### Scenario: 非必需服务失败仍显示明确异常
- **WHEN** Work 汇总为 Degraded，某个非必需 Service 确认为 Failed，而 Agent 或其他服务仍可用
- **THEN** 用户直接看到该服务的失败事实、原因与详情方向，Work 汇总和服务异常分别表达，其他可用入口不因该服务失败被伪装为失败

#### Scenario: 正常启动与失败分别表达
- **WHEN** 首次未显示应用的 Service 当前确认为 Starting，随后转为 Ready 或 Failed
- **THEN** 启动时显示所属任务及四格占位；Ready 沿原入口规则打开应用，Failed 显示明确失败及详情/日志入口，终态不等待动效周期

#### Scenario: 安全诊断可以完整查看
- **WHEN** 原 Service 返回带安全错误码、失败阶段、退出码、修复建议及关联标识的故障
- **THEN** 所属详情保留这些实际字段，主要提示仍以名称、失败和下一步组织，退出码零及其他合法值按原值表达，日志为有界快照且不自动触发服务控制

#### Scenario: 旧错误格式及部分诊断缺失
- **WHEN** Service 只有旧字符串错误、空错误、未知错误码或部分字段不合法
- **THEN** 仍显示已确认的服务状态与安全回退说明，可取得的合法字段不丢失；不输出对象字符串、伪造阶段或猜测应用内部异常，不因缺少诊断隐藏失败

#### Scenario: 多服务与无网页服务的对象入口
- **WHEN** 同 Work 有多个服务、一个以上故障或故障服务没有 Web 端口，用户查看摘要并打开详情
- **THEN** 摘要计数只基于可靠目录，单故障直达原服务、多故障进入现有管理列表，各详情与日志始终绑定正确服务，普通管理和正常服务入口仍可达

#### Scenario: 观察中断保留最后事实
- **WHEN** 已确认 Starting 或 Failed 的服务目录读取失败，随后只读恢复成功
- **THEN** 中断时标记最后状态及当前未确认，未确认的启动动画停止，失败证据保留且无自动控制；恢复后按新确认事实更新，不将读取失败当作空目录或服务已恢复

#### Scenario: 旧对象响应不能串入新对象
- **WHEN** 原服务诊断或日志读取尚未返回，用户切换服务、Work 或身份后旧结果到达
- **THEN** 原结果不替换新对象详情、不错误关联 Operation、不清理或聚焦新 Chat，查看和关闭仍没有服务修改或 Run 请求

#### Scenario: 已打开的应用保留原保护
- **WHEN** 同一应用已挂载，出现符合原保留条件的短暂 Starting 或普通后台读取
- **THEN** 保留原 iframe 文档和应用输入，不为四格占位重挂页面；Service 真正 Failed、Stopped、Disabled 或端口失效时仍按原访问边界处理
