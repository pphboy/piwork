## ADDED Requirements

### Requirement: Chat 按真实对话顺序合并历史与实时内容

Desktop SHALL 在同一 Session 内按可信历史顺序和已知 Run/消息身份合并分页历史、实时消息与工具活动。旧消息及其 Run 状态 SHALL 保留在所属轮次，不得因读取、合并或新消息受理而移到新轮次之后；无法确认归属或顺序的内容 SHALL 保留并明确未确认，不得按文字或时间猜测绑定。历史重读 SHALL 保留尚未在历史中确认的已显示输出，直到同一内容被完整替换或明确表明无法恢复，且不得重复显示。页面刷新、游标过期恢复及加载更早消息 SHALL 不改变真实顺序或隐式提交、取消 Run。

#### Scenario: 旧取消轮次与新的数字消息
- **WHEN** 已保存对话中旧 Run 为 cancelled，随后同一 Session 的“1”和“4”两次 Run 成功，且历史和实时消息混合加载
- **THEN** 旧取消状态随旧轮次显示在“1”和“4”之前，两次新 Run 各自显示成功，消息及正文不重复

#### Scenario: 历史不完整或读取失败
- **WHEN** 历史分页、Run 重读或游标过期恢复尚未覆盖已显示的实时正文，或读取失败
- **THEN** 保留已知正文与原 Run 归属并提示未确认，不用空结果覆盖，不猜测缺失内容

#### Scenario: 同文不同轮次
- **WHEN** 不同 Run 含相同用户或 Agent 文本、相同工具名称，历史分页以不同顺序返回
- **THEN** 按消息和工具的可确认身份合并，各轮次保持独立，不按文本、工具名或最近 Run 去重或绑定

### Requirement: 提交状态与 Agent 状态属于对应消息

Desktop SHALL 在用户提交时立即在原 Session 对应用户消息位置展示提交快照及“发送中”，紧随文字使用既有全局三点等待组件，文字和动效垂直居中。可靠受理后 SHALL 将该消息与原 Run 合并一次；明确失败和结果未知 SHALL 在该消息附近表达并保留恢复入口、提交快照及原键的安全语义。未知结果 SHALL 仅按原键只读核对，不自动重发；后续编辑与图片草稿仅在确认受理时按原快照消费。

Agent 所属 Run 处于真实 accepted/running 时 SHALL 在该轮回复位置显示明确的进行中状态及文字后的全局三点组件；工具执行和正文流式输出期间 SHALL 继续表达真实进度而不制造多个重复等待提示。取消中、断线未确认、失败与终态 SHALL 如实区别，终态后移除进行中提示；旧 Run 的结果和状态不得成为新 Run 的状态。中英文、窄屏、键盘以及减少动态效果遵循现有 Desktop 规则。

#### Scenario: 发送受理与继续编辑
- **WHEN** 用户发送一条消息并在等待受理期间编辑下一条草稿
- **THEN** 原消息显示发送中，受理后只有一条对应消息且状态更新，后续草稿保留

#### Scenario: 结果未知
- **WHEN** 发送响应丢失且未确认是否已受理
- **THEN** 原消息显示未确认和原提交核对入口，用户输入及原键保留，不自动再次发送

#### Scenario: Agent 生成和工具执行
- **WHEN** 当前 Run 等待回复、执行工具或流式输出正文
- **THEN** 在所属回复位置显示一个对应进行中状态，三点位于文字后且居中对齐，详情不遮蔽状态；终态后等待提示消失

#### Scenario: 观察连接失效
- **WHEN** 已受理 Run 的观察断开但执行状态尚未确认
- **THEN** 保留当前消息和已有回复并显示连接或状态未确认，不假称已取消、已完成或继续生成

### Requirement: 停止并发送使用停止图标并保留组合动作语义

在已确认支持 Stop and Send 且存在可取消活动 Run 时，发送位置 SHALL 使用居中的停止方块图标。按钮的可见悬停提示和可访问名称 SHALL 明确表示停止当前执行并发送新消息；点击或符合现行键盘规则时仍执行 CONV-CANCEL-SEND-001，不能只取消或更换目标。未支持能力、空输入、未知活动状态和旧客户端 SHALL 遵循现有准入及恢复规则。

#### Scenario: 活动 Run 中提交新消息
- **WHEN** 活动 Run 已确认，用户输入合法消息并选择停止方块按钮
- **THEN** 图标及提示表达停止并发送，原目标结束后按原组合动作受理新消息，失败或超时保留输入
