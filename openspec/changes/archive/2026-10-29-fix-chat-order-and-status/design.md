# Design

## Context

用户提供的 Work 只读历史确认：旧 cancelled 轮次在“1”“4”之前，而截图把旧轮次放在末尾；“1”“4”对应的 Run 实际成功。四个已查 cancelled Run 没有正文增量，因此不能从中证明正文丢失或取消源。合成投影测试在原实现上复现了 `saved + live` 将旧轮次追加到末尾，修复后的浏览器测试验证了相同重读路径及 Run 状态归属；这确认了可产生所报症状的一条路径，不用于追溯旧 Run 的取消发起者。

`apps/desktop-webui/src/history-projection.ts` 将保存的投影与未匹配实时消息合并时整体返回 `saved + live`，是需要复现的候选；`adapter.ts` 的终态读取以投影替换指定 Run。`runs.ts` 在中止或失败异常分支以空最终结果结束，`pi-sdk-executor.ts` 将增量发出，而 `packages/work-store/src/store.ts` 会压缩旧事件。分别存在正文不能从最终结果或压缩后事件恢复的风险。详情见 proposal 和本变更规格。

**Goals:** 确定实际错序路径，建立可恢复的消息身份与顺序，清楚表达提交和回复状态，并保护已输出正文。

**Non-Goals:** 改变 Stop and Send 的权限或执行协议；修复不存在于已保存历史和事件中的旧正文；自动修改用户 Work、发送消息、部署或发布。

## Decisions

### 按身份和可靠顺序合并

先用合成的历史分页、已受理消息和实时流构造用户截图场景，验证 `saved + live` 及跨快照排序是否为根因。`HistoryProjection` 按原消息/Run/工具 ID 合并，保留来自服务端快照的排序，并为本地提交保存其在当前 Session 的锚点；实时内容插入对应轮次，不无条件放到所有已保存内容之后。跨快照的 `entryOrder` 是快照内坐标，不能直接把不同快照的序号当全局时钟；按已知身份重叠对齐，顺序无法确认时保留内容并显示未确认，而不以正文、工具名或时间猜测。保留分页、重复事件去重及同文不同 Run 的独立身份。重读失败或未完整覆盖时不能用空结果删除实时内容。

仅按时间排序不能解决快照与实时内容的归属，也会误排同一 Run 多个工具块；仅整体替换会丢失尚未保存的增量。

### 提交快照与 Run 绑定

`adapter.ts` 在发起提交前建立以身份代次、Work、Session 和原 submissionKey 为范围的临时用户消息，包含文字与图片快照；`app.ts` 在该消息旁展示发送状态。受理响应或原键只读恢复确认同一 Run 后，原消息转接到真实 Run，避免新增第二条；未知和明确失败仍按原意图显示检查或错误入口。后续编辑与图片引用独立，只有确认后消费相应提交快照。身份或 Session 切换、迟到响应均不能污染其他视图。保留现有不自动重发与 Stop and Send 超时行为。

### 保护部分输出

`pi-sdk-executor.ts`、`runs.ts` 与 `work-store` 协作，在文字事件对观察者可见前持久记录可恢复的正文和其 Run 内顺序；事件压缩前原子保留覆盖被裁剪文字的持久检查点。终态为取消、失败或中断时仍保留检查点，并明确区分部分正文与成功最终结果。历史读取优先以可验证身份和片段范围对齐 SDK history 与检查点，避免重复与文字/工具顺序丢失；不得因为 `finalText` 为空而用空内容覆盖已有片段。对现有记录只读取实际存在的内容，事件已裁剪且无保存内容时不声称可恢复。

持久方案须保持有界读取、快照一致性和事件序号/游标语义，保证压缩或进程中断时检查点与删除事件之间没有丢失窗口；检查私有数据库 schema、快照导入导出及冷历史验证。若不得不引入新 schema 或对外契约，须同步版本、生成产物、兼容校验和跨语言测试；不能仅在 UI 内缓存作为持久恢复方案。成功 Run 的原结果及取消竞争语义保持不变。

实现调查确认 `run_events` 的序号必须连续，已有事件不能被重写，且保留窗口为 10,000 条；`final_text` 只有一个最终字符串，无法表示正文与工具交错的多个片段。因此持久检查点应独立于事件保留窗口，不能通过无限保留事件或复用错误字段实现。后续实现采用独立、分块的输出记录：保存原 Run、事件身份和顺序，在追加文字/工具事件的同一 SQLite 事务中写入；读取仍按现有片段预算分页。该结构使用 history schema 6，并同步旧 schema 4/5 的静态读取、受控升级、Go/TS 冷验证和完整包保留；完成这些兼容工作前不能将存储任务标记完成。

Core 对已压缩事件返回带 `CURSOR_EXPIRED` 的 HTTP 416，Desktop 同时兼容原 410 恢复路径，不把其他 416 当作游标过期。SDK 消息的块 ID 与实时流事件 ID 可能不同，因此历史协议可选携带已验证的 `streamId` 和 `streamOffset`：Agent 逐字节核对同一 Run 的检查点，并以工具调用身份确认边界后才提供坐标；Desktop 仅在已读取片段完整覆盖且字节匹配时替换对应实时内容。旧 Agent 不提供坐标时保持兼容，不能证明对应关系的内容保留并标记未确认。

旧 Agent 的整段历史重读和 410 恢复使用同一合并规则：仅以 Run 和真实消息或工具身份对齐；未知身份的已显示正文保留并标记未确认，终态 `finalText` 按原 Run 独立锚定。没有消息 ID 的旧响应只在完整响应未变化时复用其快照内位置，不能用相同文字推断跨快照身份。恢复活动 Run 时保留已读正文，事件重放与已保存内容的关系不明时明确标记，读取失败不抹去已知内容。

### 状态和图标

`app.ts` 和 `public/style.css` 在消息行表达本次提交状态，在对应 Run 的回复区域表达 Agent 状态；工具活动和 Run Details 保留各自含义。复用 `pending.ts` / `apps/ui-shared/controls.css` 的统一三点，文字在前、点在后，使用同一行高和垂直居中；中英文使用现有 locale 机制。停止方块作为 Stop and Send 图标，保持当前发送按钮几何位置、可见 hover/title 与键盘焦点及准确无障碍名称，仍调用原指定 Run 的组合动作。视觉参考 [原型](prototype.html)，它只是演示，不能替代真实错误、图片和多 Session 验收。

## Risks / Trade-offs

- [排序证据不足] → 首先在真实身份和分页边界下复现；对无法确认顺序的历史不臆测。
- [重复或丢失增量] → 以 Run、事件及内容区间关联，覆盖文本与工具交错、长输出、压缩和重启；异常时保留已知显示并报告未确认。
- [新增持久格式影响旧快照] → 保持能力协商与旧历史只读兼容；如需 schema 或契约变化，同步迁移、静态验证、生成与跨语言测试。
- [停止方块被理解成只停止] → 显示准确提示及可访问名称，保留组合操作前的输入和目标校验，覆盖键盘与窄屏。

## Migration Plan

先以合成数据完成实现及浏览器验证，重新构建 Desktop 并同步 Go 嵌入资源；必要时更新 Agent 镜像和兼容性检查。部署使用现有发布流程，变更不自行部署。回退时保留 Work 数据及已受理 Run，不重放；若引入新历史格式，先验证旧版本是否能安全读取，不能安全读取时保留新版读取能力再回退前端。
