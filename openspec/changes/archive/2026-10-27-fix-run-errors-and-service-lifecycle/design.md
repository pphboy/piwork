# Design

## Context

见 proposal。当前 `apps/agentd/src/pi-sdk-executor.ts` 在 SDK 返回错误后抛出固定异常，`runs.ts` 把多数异常记为可重试；Core 侧模型 Test 已有安全分类，但走独立 Go 请求，不是实际 Run 的证据。Service 创建通过 Agent SDK、MCP stdio 和 mTLS gRPC 到 Core，`CreateServiceRequest` 目前没有 Run 归属；Agent 的 `RunManager.recover()` 只标记中断，Core 的服务恢复独立运行。`service_recovery.go` 的巡检在已退出路径只写 observed 状态；`service_read.go` 仅投影认可的安全诊断。

Run history 归 Agent 私有存储，服务定义及 Docker 实例由 Core 管理。Work 单 Run 槽、幂等受理、Work 控制版本、精确 Docker 身份、已有恢复预算、Work 停止及冷快照栅栏均须继续生效。Agent bash 并不总有目标镜像中的 Python 等工具。

## Goals / Non-Goals

**Goals:**

- 将同一次实际模型请求、Run 终态和安全处理方向可靠关联。
- 在独立进程、网络丢失和迟到创建的情况下证明临时 Service 的归属与最终收尾；清理事实可以查询且日志可理解。
- 针对已确认事实解释当前 Service 和 Work 状态，避免错误退出阶段或凭空补造退出码。

**Non-Goals:**

- 不建立通用任务队列或为普通 Service 改变持续运行、退出判定和恢复预算。
- 不按名称、退出码或历史外观识别并自动清理旧 Service；不扩大容器、文件或模型管理权限。
- 不把原始供应商响应或容器输出放进安全诊断；不因错误而重放 Run、工具调用或业务副作用。

## Decisions

### 1. 在模型请求边界形成安全分类

在当前 Run 的实际 SDK/供应商适配边界捕获与该次模型请求绑定的可信 HTTP 状态或受支持协议结构化错误类型，立即映射为有限内部类别，再由 `RunManager` 生成固定消息及 `retryable`。401 仅确认认证被拒；只有明确的协议错误类型能支持“Key 无效”的更具体表述。403 单独说明权限/模型访问，429、网络、取消及未知错误不能归为认证。不要用任意异常文字的子串或工具输出中的 `401` 猜测。SDK 将状态折叠为文本时，需要在其可证明的请求边界保留最小安全信息；不得为分类向公开事件、SDK history 或日志保存原始正文。若无法可靠识别则保留安全通用错误。

Run 公开协议已有 `code/message/retryable`，优先复用并沿事件、读取、历史及 Core 投影保持一致。Desktop 同时保留结构化分类和消息，按当前用户权限给出管理入口或联系管理员的方向；旧 Agent 的通用错误继续可读。替代方案是透传供应商异常或仅修改 UI 文案，前者可能泄漏凭据，后者无法修复分类和重试语义。

### 2. 显式临时生命周期和可信 Run 归属

在现有 `service_create` 增量协商临时模式，原请求保持普通持久 Service 语义。临时模式由运行中的 Agent 工具执行桥从实际 `RunExecutionContext` 注入 Work、Run 和当前代次身份，经现有 mTLS 到 Core；模型不能提交或替换归属字段。Core 校验当前受信 Agent、Work/代次及仍有效的 Run 创建许可；不支持该能力的旧端点明确拒绝临时模式，不能静默降级为常驻服务。复用现有工具授权和配额，不提供 Docker 宿主访问。

MCP 入口仍为 `service_create`，但临时创建使用独立的增量 gRPC 方法；旧 Core 对未知方法返回不支持。不得仅在旧 `CreateService` 请求增加字段：旧 protobuf 端可能忽略未知字段并误建普通服务。能力协商和真实 Run 绑定仍为发送临时请求的前提。

Core 在服务受理事务内持久保存临时标记、Run/代次、服务身份、创建 Operation、幂等指纹和清理目标；接收响应丢失时按原键返回同一对象。为实际 Run 建立 Core 侧持久创建许可，临时创建和关闭该许可在 Core 存储中原子排序；令牌与代次绑定，模型不可设置。Agent 终态通知丢失时由 Core 核对 Run 或确认代次失效后关闭许可。已在终态之前派发但迟到的请求也必须纳入同一清理目标，只有关闭许可并确认全部已受理及迟到副作用后才能报告清理完成；不能把仅有的进程内回调作为栅栏。

延续现行 Core schema 1，将临时归属和清理数据保存在现有 `control_metadata` 的专用命名空间。在首条不兼容记录写入前，持安装锁发布并同步一个固定、空内容的私有兼容性标记；当前版本识别该标记，而旧 Core 的严格根目录校验会在打开数据库业务写入前拒绝它。标记一经发布不自动移除；重启时若已存在临时记录而缺少标记，必须拒绝启动，不能以旧版可打开的状态继续。该顺序不改变 schema 1 的完整 WAL 校验和普通安装行为，也不把手工删除标记当作支持的回退方法。

临时语义不由名字推断，旧服务永远不自动转为临时服务。显式的一次性模式以已确认进程退出作为完成事件：退出码 0 表示该次命令正常结束，非 0 是该次检查失败；这不是普通常驻 Service 的 readiness 或健康判断。需要短暂对外监听的临时服务继续按其 readiness 观测，直到被收尾。临时对象不作为 Work 常驻应用的降级原因，但其执行失败和清理状态必须可查。

允许受权 Agent 按原临时对象查看结果和有界输出，再显式结束；Run 结束时即使 Agent 没发清理请求，Core 仍收尾。对最后一个结果的保存、输出读取与实例删除按原实例身份协调：不替换为其他实例输出；需要保留的日志走现有授权内容/归档边界，不把输出复制进全局安全日志。清理失败不能伪造读取或完成。

### 3. 终态驱动与可恢复清理

```
agent Run -- create temporary --> Core durable owner + create Operation
     |                                  |
     +-- terminal/cancel --------------> cleanup requested
     +-- daemon lost/fenced -----------> cleanup requested
                                        |
                         stop/remove exact instance + release quota
                                        |
                      confirmed / cleanup pending / retry / confirmed
```

正常终态、取消及 Agent 恢复中断通过可信通知触发；通知丢失时 Core 对已记录归属核对相应 Run/代次，或在已确认旧代次死亡/被栅栏取代后收尾。Core 重启不等于仍存活的 Agent Run 已失败：能核实原 Run 仍活动时继续观察；连接失败但生死未知时保持未确认、重试查询，不推测其结束。未核实的目标不能被清理或被复活。

清理请求与创建许可原子排序：Run 已结束或代次失效后不再允许新临时创建；已接受的创建可能迟到，须按服务身份和控制栅栏持续收尾，不能报告清理成功后又出现运行实例。清理状态持久化并使用稳定幂等身份，Docker 或存储不可用时保留待重试、错误和可观察入口；依赖恢复后自动重试，不以空检查或超时宣称完成。只移除精确绑定的受管容器和定义引用，保留共享 workspace 与其他 Service，实际停止/移除确认后才释放资源配额。

当前 Run 原结果不被清理失败覆盖；清理拥有独立的 Work-scoped 状态/Operation 与关联身份。Core 必须有可恢复的触发和重试机制，不能只依赖 `onSettled` 内进程内回调。清理与正常 Work Stop/Delete、Core shutdown、snapshot gate 共用控制顺序和关闭预算：确认不了时保留未完成状态，冷导出在清理尚未确认时不发布；恢复不得重启需要清理的临时实例。正常清理后可按现有 tombstone 和历史约束进入完整包，不把 live Run 归属当作目标安装的执行许可。

### 4. 常驻服务诊断和 Work 投影

`service_runtime.go` 捕获启动阶段退出，`service_recovery.go` 在巡检运行后退出或实例缺失时形成安全诊断；每条路径都按目标版本/控制栅栏持久写入状态和诊断，保留可确认的退出码包括 0，缺失和 Docker 不可达不伪造退出。将当前阶段与安全文案一致化，不再把运行后退出描述为“就绪前”。重试期间保留原始原因与当前恢复状态，成功就绪、确认禁用或移除时清除当前故障，历史 Operation/诊断保留。不得改写已成功的原创建 Operation。

`service_worker.go` 汇总全部启用的普通服务：可选异常维持 Degraded、必需服务沿既有 Failed 语义；一个服务恢复时仍须考虑其余故障。`desktop-webui` 复用已确认的服务列表、详情和日志，区分失败、恢复中、未知及未确认读取；不可用详情不臆测原因，晚到响应不能覆盖新状态。

### 5. 清晰的安全日志和可查询结果

为临时生命周期提供 Work 授权范围内可查询的独立清理记录/Operation，关联 Work、Service、Run、创建及清理 Operation/关联 ID；仅在相应身份真实存在时提供。结构化日志记录 UTC 时间、清理触发类别、阶段、开始/完成/失败/待重试、确认状态和安全错误码；保留有界的持久结果与截断信息，明确清理仍在执行、依赖不可用或归属无法确认。重启、实例删除和查看旧 Run 时仍可追踪；中断和重试不制造虚假成功。

安全日志不记录 API Key、请求头、完整命令/环境、宿主路径或容器输出。容器输出仍作为受 Work 内容授权的有界非可信日志访问；它与服务退出诊断及清理日志是不同来源。诊断写入失败时按既有持久化故障约束报告，并保留可恢复记录，不将日志收集失败替换为原始故障。避免将不可导航的 correlationId 误当作 Operation ID。

## Risks / Trade-offs

- [临时创建与终态竞争] → 持久归属与创建许可在受理时绑定，终态栅栏及迟到实例清理以并发测试覆盖。
- [SDK 不提供可靠状态] → 使用可证明的请求边界捕获安全类别；保留通用回退并以合成真实 SDK HTTP 测试验证两种协议。
- [依赖不可用导致无法即时清理] → 持久展示 pending/失败及自动重试，绝不误报已清理；Docker 恢复后继续。
- [旧版本不了解临时语义] → 通过能力协商拒绝危险降级，原请求仍遵守旧契约；迁移先升级 Core，再显式采用兼容 Agent。
- [快照与新内部记录冲突] → 导出前确认无未完成临时清理，已完成对象按现有 tombstone/归档语义处理，跨安装不恢复原 Run 权限。

## Migration Plan

新增记录缺省为普通 Service；不推断、清理或改写历史 `sb-probe3` 一类遗留对象。先部署兼容 Core/契约，再通过既有镜像选择与包 Apply 显式采用兼容 Agent 和脑包；旧 Agent 继续原聊天及普通服务，无法安全使用新临时模式时明确不支持。WebUI 构建资源随 Core 更新。涉及持久存储的回退须先停止相关 Work、完成临时清理并备份配套数据；旧二进制不得直接打开不兼容的新状态。
