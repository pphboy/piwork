# Proposal

## Why

Core 将不可变镜像的完整能力验收结果限制在进程内，重启后重复导出、落盘和遍历大镜像；已有 Work 恢复又依赖默认环境准备，服务入口受全局 Ready 阻塞。已观察的 Windows MicroVM 无新镜像加载启动中，HTTP 约 5 秒可用而完整就绪约 70 秒，需要修正 Core 的验收结果生命周期和恢复依赖，而不是放宽校验或调整超时。

## What Changes

- 在本安装内持久保存完整成功的静态镜像能力及确定性的镜像包环境探测结果，绑定实际 Engine 身份、不可变镜像身份、类别、平台与独立规则版本；重启后轻量复核再复用，失效时重新完整准备。
- 保留同键共享、独立取消、有界资源和清理证明；有效记录命中不经过重型扫描队列，失败或清理未确认不发布成功。
- 将已有 Work 的恢复调度与默认环境准备解耦，按每个 Work 的实际镜像、持久意图、资源栅栏及当前代次验证开放能力。默认配置变化不取消无关 Work 恢复，也不隐式升级其镜像。
- 全局基础/完整就绪继续真实表达默认环境与启动恢复状态；已验证 Work 的服务可在全局尚未 ready 时独立开放，未验证或关闭中的入口保持拒绝。此项明确调整原有全局网关恢复门槛，不增加公共状态 DTO 字段。
- 增加安全启动阶段计量和可重复验收：参考 Windows WHPX 2 vCPU / 4 GiB、三个已验收 Agent 镜像版本、一个运行目标 Work 和一个 Service，日常 MicroVM 启动 P95 ≤ 25 秒；VM/Docker 存活时 Core 重启 P95 ≤ 10 秒。整 VM 预算由所有者明确从 20 秒调整为 25 秒；两组各至少 20 次，所有失败保留，重启全量镜像导出/扫描为零。
- 首次安装、新镜像和首次建立记录分别计量，保留完整校验；不将日常重启预算宣称为这些冷路径预算。
- 按所有者明确要求，验收仅操作隔离 Core 与 MicroVM，不重启 Windows 宿主整机，也不将整机重启作为完成条件。
- 核验后修复候选的后续复验按所有者最新决定收敛：保留原已通过的两组各 20 次完整性能基线，使用匹配新制品的已完成 Core 20 次、整 VM 7 次实际启动回归收尾；不再追加重复启动，不把新候选的 7 次整 VM 样本宣称为重新完成 P95 基准。

## Capabilities

### New Capabilities

无；扩展现有运行准备、启动恢复与诊断契约。

### Modified Capabilities

- `runnable-work-runtime`：成功准备结果跨 Core/VM 重启复用、Engine 与规则隔离、持久发布和失效规则。
- `core-service-startup`：默认准备与已有 Work 恢复解耦、按 Work 核验后准入、保持全局就绪语义，以及重启性能验收。
- `work-diagnostics`：启动、持久复用、实际全量检查及恢复阶段的安全计量。

## Impact

- Core：`internal/dockerengine`、`internal/imagestatic`、`internal/preparationcache`、`internal/corestore`、`internal/coreapp`、`internal/app` 及对应测试/验证脚本。私有派生记录复用现有存储，不新增业务启动参数、宿主工具依赖或公开 HTTP/RPC 字段。
- 原完整镜像校验、包目标兼容性、Work context/当前 Agent 验证、Stop/Apply/快照/文件栅栏、持久恢复预算及 45 秒关闭预算保持。`.work` 导入校验不使用安装内验收记录替代。
- 依照已实现的 `simplify-linux-delivery` 使用当前 `piwork-core` 三参数入口；不恢复主规格中尚待同步删除的旧命令，不改写其他变更。
- 依赖准备/就绪说明须同步既有双语部署材料、单机示例、官网生成内容及相关检查，根 README 保持精简。
- 修复实现归属本 Core 仓库。所有者已授权为最终验收集成 MicroVM 本地候选，须冻结并核对实际 Core、镜像与 MicroVM 输入；该授权不包含对外发行或改变 MicroVM 性能机制。Windows 验收未通过前不得宣布完整优化达标；若发现启动器额外瓶颈，单独报告其证据和所属范围。
