# Spec Delta

## MODIFIED Requirements

### Requirement: 等待状态按对象防重复并允许离开和独立操作

**Identifier:** DWUI-012

除当前 Core readiness 尚未准入或明确进入启动恢复的统一门禁外，Desktop SHALL 只限制该提交的重复入口和同对象的冲突修改，禁止用一个普通异步动作禁用整页按钮。同一 Work 文件修改串行，同一 Service 控制提交串行，同一配置提交串行；同 Work 生命周期提交期间限制冲突写入。取得 acceptance 后提交锁 SHALL 释放，后续准入仍按真实对象状态及既有控制语义，允许合法 Stop 取代未完成 Start；不能将 Operation 观察当作全局锁。身份变更提交期间阻止新的平台修改，既有匿名 Inspect 规则保持。

Core 启动门禁 SHALL 仅限制尚未发出的业务动作，不以普通 Operation 观察、单个 Work 恢复或已有可用工作区的一次读取失败触发全页限制。明确启动恢复期间，账号、适用于当前模式的连接配置、状态诊断、只读恢复与合法返回继续可用；已有请求或已接受任务不因门禁出现被取消或自动重提。Core 就绪后 SHALL 重新按对象事实、未知结果保护和实际能力决定准入，不批量释放原对象的锁。

Service 控制提交的对象 SHALL 按发起时的 Work 与 Service 身份绑定，不包含浏览器入口端口。切换端口、关闭再打开详情或换用另一控制入口不能绕过同一 Service 的在途冲突锁；其他 Service 的合法动作保持可用。Service 预览、入口准备及其缓存仍按 Work/Service/port 区分。

等待期间 SHALL 保留普通 Close/Back、复制及无关对象的合法动作，导航仍检查脏草稿。关闭普通详情或离开模块只结束当前展示/读取观察，不暗中取消远端 Operation、Run 或已提交修改；DWUI-009 的明确导出交付意图与面板展示独立，继续其必要只读观察和已授权后续步骤。未提交 Inspect 的 Cancel/Escape 仍释放本地暂存；提交中/未知/已接受 Import 保留原身份并只停止展示。界面 SHALL 明确这些不同的关闭含义。

反馈 SHALL 绑定发起时的 Core/账号、Work/对象及该次动作。切换对象后晚结果不能打开旧弹层、覆盖新内容/草稿或显示为新对象的成功；同身份已接受操作仍能按原 ID 找回。新身份不得取得旧内容或传输。失败/终止后 SHALL 释放相应等待状态，保留已有安全约束；未知修改不能通过重新启用按钮暗示可直接再次提交。保存期间允许继续编辑时，成功只确认已提交草稿，新编辑仍为 Unsaved。

未知修改的只读核对 SHALL 匹配原 Core/账号、Work、动作及涉及资源，并依据实际返回对象判断核对范围。查询其他 Work 的 Operation、同 Work 的无关 Operation 或未确认关联关系的记录不得解除原动作的未知结果锁；不得因为一次查询成功而批量解除当前 Work 的生命周期、传输和 Agent 锁。已有接口能够确认原目标的当前事实或原业务身份时，才可恢复对应动作的既有准入，并保留原提交结果未知与当前事实已核对的区别；无法确认时继续提供原对象核对入口，不自动重发、不暗示可直接重试。

#### Scenario: 等待下载时关闭或执行独立动作
- **WHEN** 当前 Work 的下载准备尚未完成，用户关闭 Export 并查看另一 Work
- **THEN** Close/Back 可操作，另一个 Work 的合法动作不被禁用；原准备不会自动再次提交，原结果可在原上下文找回，未手动暂停的有效原交付意图完成后最多一次发起原文件下载并明确原 Work；不会打开旧弹层或覆盖新对象，身份失效则不得自动交付

#### Scenario: 文件选择入口防重复
- **WHEN** 同一 Work 正在上传，用户再次通过文件选择或键盘触发上传/删除
- **THEN** 第二个冲突修改未发出，当前上传和原因可见，不建立隐藏队列；其他 Work 的合法操作不受此锁限制

#### Scenario: 晚返回与继续编辑
- **WHEN** 用户切换 Work/Core/账号，或在 Save 期间继续编辑，旧动作随后返回
- **THEN** 旧反馈不进入新对象或新身份；同对象保存只确认提交版本，新草稿保留；旧请求的结束不会释放另一动作的锁

#### Scenario: Operation 观察与目标取代
- **WHEN** Start 已接受并正在观察，用户在既有准入下显式 Stop
- **THEN** 可以提交新的停止目标；两个 Operation 身份分别保留，旧 superseded 不被描述为当前启动成功

#### Scenario: 切换端口不绕过 Service 控制锁
- **WHEN** 同一 Service 的 Restart 响应尚未返回，用户关闭详情、切换浏览器端口并重新打开该 Service 的控制入口
- **THEN** 第二个冲突控制请求不会发出，原目标与等待原因仍可查看；其他 Service 的合法控制不受此锁限制，预览入口仍按所选端口区分

#### Scenario: 未知结果核对仅恢复对应原对象
- **WHEN** Work A 的 Start 返回结果未知，用户查询 Work B 的 Operation 或 Work A 的无关 Operation，随后核对原目标
- **THEN** 无关查询不会解除 A 的未知结果锁或产生第二次 Start；只有匹配原身份、动作对象且能够确认相关事实的核对才恢复对应准入，原提交未知不被改写为确定成功，其他未知动作不被批量解除

#### Scenario: Core 启动门禁与普通对象等待不同
- **WHEN** Core 明确恢复中，或 Core 已就绪而单个 Work 的 Start 尚未完成
- **THEN** 前者阻止新的业务动作并保留安全恢复入口；后者仅按该 Work 的状态限制相应动作，其他 Work 可正常使用，合法 Stop 仍遵守原准入

### Requirement: Desktop 准确呈现 Core 启动恢复状态

Desktop SHALL 区分 Core 可达且正在启动恢复、明确未就绪、不可达以及状态读取未确认；可解析的未就绪响应不得因 HTTP 503 被解释为 Core 不可达。首次进入、刷新和直接访问 Work 或 Service 路由时，在当前身份基础 readiness 尚未确认前 SHALL 不开放依赖 Core 的业务入口；明确处于 RECOVERING 时 SHALL 使用所属原型中的启动等待页，不同时展示可操作的 Work 列表、创建、导入、生命周期、配置、文件或运行入口。账号、语言、只读连接与诊断以及当前模式支持的合法导航 SHALL 保持可用，不增加浏览器授权流程。

恢复 SHALL 自动进行有界只读观察，并适用于门禁页面及已进入工作区的恢复状态，不依赖 Work 列表是否正在展示。取得当前身份、当前检查代次的基础就绪确认后 SHALL 自动解除门禁、恢复原目标路由并读取相应对象；Core 基础就绪不保证每个 Work 或非必需 helper 均已可用。明确失败、缺配置、不可达、状态读取超时及自动观察预算耗尽 SHALL 分别显示实际原因或未确认和可操作的恢复方向，停止对应启动动效，不无限沿用旧 RECOVERING。

已进入工作区后确认 Core 正在恢复时，Desktop SHALL 暂停新的相关业务入口，在原上下文提供恢复状态，同时保留已读取内容、未提交草稿、选择和适用的 Service 容器。此限制 SHALL 不取消已接受远程任务，不重发用户写入，不因周期检查重建编辑器或 iframe；此前已明确授权的交付继续遵循其原意图及实际权限。单次普通读取失败 SHALL 仍沿用最后确认事实与局部未确认规则，不能据此假定 Core 正在恢复或撤销整页。

启动状态及动效 SHALL 依照 ui-language 的 Core 启动例外和本变更原型，提供一致中英文、基本键盘、窄屏及减少动态效果行为。前端隐藏和禁用 SHALL 配合动作执行前的同一门禁检查；服务端实际权限与业务准入继续生效。

#### Scenario: Core 启动恢复
- **WHEN** Core 返回有效的 RECOVERING 或其他明确表示正在准备的状态
- **THEN** 首次进入显示启动等待页，屏蔽业务列表和操作，状态自动只读更新；不显示 Core 不可达、虚假故障或重复 Alert

#### Scenario: 不可达及失败
- **WHEN** 状态请求失败或 Core 确认恢复失败
- **THEN** 分别展示连接不可达、状态未确认或真实失败及只读检查入口，不把旧启动状态当作当前事实，不新增业务写请求

#### Scenario: 状态请求挂起
- **WHEN** 恢复期间的 Core 状态读取超过时限，或用户隐藏页面、切换身份
- **THEN** 取消或暂停该只读观察，超时显示状态未确认并允许手动重查；旧响应不得覆盖新状态，返回可见页面后按当前身份确认

#### Scenario: 直接进入 Work 或 Service 地址
- **WHEN** 已认证用户刷新或直接打开 Work 及 Service 路由，而 Core readiness 尚未确认或明确正在恢复
- **THEN** 目标路由经过同一门禁，不能通过链接、键盘或已有弹层提交业务动作；Core 就绪后按原路由及目标对象实际准入恢复

#### Scenario: Core 恢复完成自动进入列表
- **WHEN** 当前身份的 Core 从 RECOVERING 变为基础 ready
- **THEN** 页面自动进入原目标或适用的列表，保留当前搜索和导航意图，并读取最新 Work 事实；不必整页刷新，也不重提 Start 或 Retry

#### Scenario: Core 就绪但部分 Work 尚在恢复
- **WHEN** Core 已基础就绪而 Work A 仍在自动恢复，Work B 已确认可用
- **THEN** 解除 Core 门禁，A 显示其实际恢复状态和安全操作，B 可使用；非必需 helper 未就绪按功能降级，不误锁整个工作台

#### Scenario: 使用中确认 Core 进入恢复
- **WHEN** 用户在 Chat、Files、Settings 或 Service 中已有内容和草稿，随后当前身份明确观测到 Core 恢复
- **THEN** 原工作区显示恢复状态并阻止新的相关业务动作，保留草稿、位置及适用 iframe；再次基础就绪后在原上下文恢复，不重复发送原提交

#### Scenario: 普通读取失败不制造全局恢复
- **WHEN** 已确认可用的工作区仅发生一次普通状态读取错误，尚未确认 Core 进入恢复或失去相应能力
- **THEN** 保留最后确认内容并说明未确认，按已有对象和能力约束处理新动作；不凭该错误改为启动门禁或取消原任务

#### Scenario: 自动观察达到上限
- **WHEN** Core 一直返回恢复中且到达本次只读观察预算上限
- **THEN** 停止本次自动等待动效，说明观察已暂停、启动结果尚未确认，保留手动检查及合法账号和诊断入口，不伪造启动失败

#### Scenario: 运行配置缺失或登录失效
- **WHEN** Core 明确报告需要配置或管理员初始化，或现有认证检查确认会话失效
- **THEN** 分别提供当前模式支持的配置或正常登录方向，不能无限显示启动等待、假造已就绪或自动重放登录与业务修改

### Requirement: Work 行只展示当前状态及有效操作

Work 列表 SHALL 根据当前确认的 observed 状态及目标显示对应状态和安全快捷动作，启动恢复中 SHALL 自动更新；上次运行保存的 Ready 或 Stopped 在当前恢复尚未核实期间 SHALL 标识未确认或恢复中，不能宣称当前已就绪或已停止。已终结的 Create、Start、Retry 等历史 Operation SHALL 不常驻 Work 行状态旁，也不得作为已无当前处理义务的失败条目堆在 Work 命令菜单中，仍可在该 Work 的操作记录与原详情中查看；未完成或未确认操作保留原身份、必要的检查入口和安全约束。读取 404 SHALL 按被查询对象表明未找到或状态未确认，不推断业务操作失败，也不能据此错误移除 Work。

#### Scenario: Core 重启自动恢复
- **WHEN** 原目标为 running 的 Work 在 Core 重启后等待恢复、启动并最终确认 ready
- **THEN** Core 恢复期间由门禁覆盖初次列表；Core 基础就绪后，列表按各 Work 实际情况展示未确认或恢复中、Starting、Ready，无需用户重复 Start 或手动刷新

#### Scenario: 自动恢复失败后重试成功
- **WHEN** 恢复尝试失败但已安排自动重试，随后 Work 恢复成功
- **THEN** 列表继续只读观察，不显示最终失败或 Retry，并自动更新为 Ready；重试耗尽则显示失败及恢复操作

#### Scenario: 历史操作已经结束
- **WHEN** 旧 Create 或 Start 已成功且 Work 当前状态发生改变
- **THEN** 行仅展示当前状态与动作，旧操作仍可在记录中查询，不附带历史成功文本

#### Scenario: 原操作查询 404
- **WHEN** 某个原 Operation 查询返回 404 而 Work 查询仍可用
- **THEN** 说明该 Operation 查询结果并保留 Work 当前事实，不将其呈现为 Work 失败

#### Scenario: Work 已恢复且菜单包含多条旧 Retry
- **WHEN** Work 当前目标与新鲜状态已确认收敛为可用，多个旧 Retry 已核实终结且无当前待确认义务
- **THEN** 行只显示当前对象状态与适用动作，菜单通过一个操作记录入口保留每条原失败结果，不逐条常驻 Check progress，不把失败改成成功

## ADDED Requirements

### Requirement: Work 当前任务与已结束操作历史分别呈现

**Identifier:** DWUI-OPREC-004

Desktop SHALL 在所属 Work 的菜单提供操作记录入口，按当前 Core/账号及已确认 Work 归属显示已知原操作的动作、结果、时间、原 ID 与详情，并可区分当前任务及已结束历史；不提供全局操作发现或跨用户历史。菜单 SHALL 以命令组织，当前需要处理的任务经一个入口查看，不把每条历史操作的进度、检查和详情按钮直接铺在菜单内。已有 Work 信息、设置、Export、原快照找回及合法生命周期命令 SHALL 继续可达。

当前任务 SHALL 包括已接受仍在执行、提交结果未知、原对象或同步尚未确认，以及明确失败且仍对应当前控制问题的任务；多个未决任务 SHALL 各保留原身份，不凭时间选择一个覆盖其他任务。已结束且当前没有匹配处理义务的任务 SHALL 归为历史；原 failed 结果保持 failed。Work Ready、Operation succeeded 或本地 terminal 提示中的任意单个信号 SHALL 不足以解除接受意图、Work/列表同步义务、记录保存失败或未知修改保护。旧 Start 结果不得解除新 Stop 的义务；当前状态和历史结果分别表达。

已知历史 SHALL 在同身份页面重载及重新登录后仍有入口，沿用既有记录保留数量和用户显式隐藏语义。展示分类 SHALL 不通过自动隐藏或删除原记录实现；本地终态提示仅协助恢复展示和读取安排，不替代 Core 当前事实、对象归属、目标版本或实际准入。旧格式记录逐条只读核实后收敛；不能将恢复读取期间的历史一律显示为新的失败或要求再次 Retry。身份切换使旧内容和响应失效。

已核实终结的历史详情 SHALL 主要提供结果与诊断，不常驻要求推进执行的 Check progress 或 Retry；当前仍需确认的对象可单独只读检查，已终结结果也可显式重新查询原 ID。未知任务 SHALL 保留原 ID 或原对象核对入口；本次未知修改未匹配确认前不得自动重发或用无关历史释放保护。历史原 Operation 返回 404/410 SHALL 说明记录无法再核实并保留适用标识，不推断 Work 失败或无限轮询。

#### Scenario: 多条旧失败转为可查询历史
- **WHEN** 同一 Work 的五条旧 Retry 已确认 failed，当前目标与 Work/列表已确认恢复为 Ready，且不存在匹配的未知结果或同步义务
- **THEN** Work 菜单不展示五组 failed 与 Check progress，操作记录仍逐条可见其原 ID、时间及失败详情，当前任务筛选不包含这些已结束记录

#### Scenario: 当前失败仍可处理
- **WHEN** 当前运行目标的最新相关任务明确失败且 Work 仍未恢复，或失败的清理仍需处理
- **THEN** 原对象表达当前失败、原因和合法恢复方向，当前任务入口仍可达；不能因任务已终态就自动移走当前问题或将其伪装为历史已解决

#### Scenario: 提交结果未知不得被历史成功解除
- **WHEN** 新 Stop 提交响应丢失，已知记录中另有旧 Start 成功且 Work 曾经 Ready
- **THEN** Stop 的原对象核对和匹配保护保留，旧成功或 Ready 不解除该义务，历史查看与重载不会再发 Start 或 Stop

#### Scenario: 多个未决任务各自保留
- **WHEN** 同一 Work 有多个来源或阶段不同的已知未决操作
- **THEN** 当前任务入口说明存在多个需核对任务，逐一提供原 ID 和检查，不凭浏览器记录时间把任一任务认作 Core 当前目标

#### Scenario: 重载不把历史再变成故障菜单
- **WHEN** 同一账号重载页面或重新登录，存在先前确认终结并已收敛的已知操作
- **THEN** 这些记录仍可在所属历史找到，必要的只读重新核实不会把它们批量恢复成当前失败菜单或影响正常 Work 准入；当前未决与旧格式记录继续按真实核对结果恢复

#### Scenario: 本地记录或读回未确认
- **WHEN** Work 显示 Ready，但原任务记录保存失败、最新控制目标未核实或 Work/列表读回仍未完成
- **THEN** 保留对应未确认说明和恢复路径，不仅凭 Ready 或终态提示收起当前问题，不删除协调依据

#### Scenario: 记录隐藏与身份切换
- **WHEN** 用户按现有规则隐藏已结束记录，或切换 Core/账号后旧查询返回
- **THEN** 隐藏只影响原记录展示且不清除当前未决协调依据；新身份看不到旧历史，晚结果不修改新身份任务、草稿和锁

#### Scenario: 原操作已不可查询
- **WHEN** 历史 Operation 查询明确返回 404/410，而所属 Work 仍可用
- **THEN** 在该历史记录说明原结果目前无法核实及适用原 ID，停止该 ID 的无限自动观察，Work 继续按自身新鲜事实显示

#### Scenario: 查看和恢复不会制造重复重试
- **WHEN** 用户打开菜单、操作记录或详情，刷新页面，恢复连接，或多窗口观察同一原任务
- **THEN** 这些行为仅做状态核对，不创建新的 Retry/Start/Stop；用户新的明确动作才按原准入受理一次
