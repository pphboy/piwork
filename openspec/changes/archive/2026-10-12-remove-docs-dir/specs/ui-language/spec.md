# UI 语言规格变更

## MODIFIED Requirements

### Requirement: 仓库分别提供可沿用的 UI 语言与产品语言

**Identifier:** UIL-001

仓库 SHALL 以中文 `ui-language` Spec 直接提供可沿用的共享 UI 视觉语言与产品交互语言，不再要求存在独立的 UI / 产品语言开发文档。Spec SHALL 定义视觉适用范围、共享语义色彩与基准值、跨页统一的页面轨道、同级一级卡片边界、内部宽度与表单网格、长内容溢出、字阶、间距、圆角、边框、控件状态、响应式和可访问性；并按页面、section、表单、字段组、列表行、详情、技术披露、反馈、异步进度及确认的容器角色定义信息组成与取舍、信息顺序、按钮主次与位置、稳定术语、界面语言、帮助与错误、选择与排序、草稿与提交、设置范围和异步恢复。

后续 Serve 界面变更 SHALL 依据本 Spec 和对应能力的有效 Requirement / Scenario 设计、实现和验证；不适用的规则 SHALL 在对应 OpenSpec 变更中记录偏离项、理由及替代方式，不另建开发文档。导航组织 SHALL 与有效 `serve-ui` 及 `ai-model-management` 要求一致，不将旧文档中的七项平级导航恢复为新的约束。

CLI Desktop WebUI SHALL 沿用共享语义颜色与产品表达原则，并由中文 `desktop-ui-language` Spec 统一规定产品语义、工作区结构、容器、视觉和交互。变更期间采用对应 delta，同步后采用主规格；Serve 的页面轨道、管理表单网格和导航组织 SHALL 只约束 Serve，不直接约束 Desktop。后续 Desktop 变更 SHALL 引用对应需求编号并记录有理由的偏离与替代方式。终端 CLI 的字符界面不受浏览器布局或 CSS 视觉令牌约束。

#### Scenario: 后续新增浏览器页面
- **WHEN** 仓库后续新增或调整一个浏览器管理页面
- **THEN** 设计与实现能按本 Spec 选取视觉令牌，以及页面、按钮、文案和反馈规则；评审可逐项核对，未说明例外的页面不另起一套视觉或操作表达

#### Scenario: 特殊场景需要例外
- **WHEN** 新界面的具体使用场景不能沿用一项视觉规则
- **THEN** 对应变更明确记录属于哪套语言的偏离项、原因和替代方式，其余规则继续适用

#### Scenario: 后续新增 Desktop 功能
- **WHEN** 后续变更为 CLI 本地 Desktop WebUI 增加界面或流程
- **THEN** 评审核对 `desktop-ui-language` Spec 的对应需求与共享颜色、文案原则；不会把 Serve 管理页的 1100px 轨道、表单网格或导航组织当作 Desktop 默认结构

### Requirement: 改动后的界面可按现有部署方式预览

**Identifier:** UIL-005

本 Spec 及其对应变更 SHALL 说明在 Core 已启动、管理员已初始化且具备本地 HTTPS 证书时，如何构建并启动独立的 `piwork-console serve` 预览最新 UI，如何在样式或文案修改后重新构建和重启面板，以及如何分别检查桌面和 360px 窄屏布局。验收 SHALL 保留代表性桌面与窄屏截图，覆盖登录、列表或表单、状态或详情页面，并能据此核对视觉与产品表达；截图不得包含真实密钥、密码或用户敏感数据。

#### Scenario: 本地预览新版 UI
- **WHEN** 开发者按有效 Spec 及对应变更中的命令示例构建并启动 Core 与面板，然后在浏览器打开其 HTTPS origin
- **THEN** 能以管理员身份查看最新样式；重新构建并重启面板后可看到新改动，而无需修改 Core 或另起预览服务

#### Scenario: 复核视觉交付
- **WHEN** 评审者检查本次视觉改动的截图和窄屏页面
- **THEN** 可对照本 Spec 核对顶栏、section、按钮位置、表单/列表、焦点、文案与状态，截图不暴露真实凭据

### Requirement: 文案准确表达动作、状态与下一步

**Identifier:** UIL-008

未经用户明确要求其他语言，浏览器 UI 自有文字 SHALL 只使用英文，包含导航、页面与 section 标题、字段标签、按钮、帮助、空态、加载／成功／失败反馈、校验提示、确认对话框、浏览器标题及无障碍名称；`html` 的文档语言 SHALL 与可见 UI 一致。导航组织与英文名称 SHALL 采用有效 `serve-ui` 与 `ai-model-management` 契约：`Overview`、`User access`、`Work setup`，以及独立的 `AI models` 入口；运行时和能力子页面保留既有深链接，`Find operation` 为按 ID 查询的辅助入口，不暗示提供 Operation 列表。本次归并不新增、移除或重排现行界面入口。UI SHALL 稳定使用 `Core`、`Work`、`Skill`、`Package`、`Operation`、`Runtime` 和 `Default Work`，不用不同名称指代同一对象。用户提供的文本、资源名称、文件内容、技术 ID、错误码及 correlationId SHALL 保留原值，不因界面语言被翻译或改写；未经确认的服务端自然语言错误消息不能直接作为 UI 英文说明，面板 SHALL 提供英文说明和下一步，并将安全的错误码、字段及关联 ID 留作辅助诊断，不让诊断串替代主要反馈。规范文档可以使用中文；终端 CLI 不受浏览器 UI 英文约束。页面与字段标题 SHALL 简短指明对象；操作按钮 SHALL 使用能说明结果的英文动词和对象，避免孤立的 `Submit`、`OK` 等含糊词。排序等重复行操作 SHALL 用简短可见动词及包含完整对象名称的无障碍名称区分目标。帮助文字 SHALL 只补充用户作决定所需的作用范围、限制或后果。加载、空集合、请求失败、结果待核实和成功 SHALL 使用不同措辞；反馈 SHALL 先陈述可确认的事实，再给出下一步。字段校验错误 SHALL 紧邻字段并说明修正方式；整页读取或提交错误 SHALL 放在对应 section 并提供可执行的恢复方式。未保存草稿、提交中、成功、提交前失败与提交结果未知 SHALL 分别表达，未知结果在重新读取当前状态前 SHALL 不提示自动重试。异步上传、Core 接受与 Operation 终态 SHALL 分别表述；不能把上传完成、已接受或旧状态写成最终成功。文案 SHALL 简洁、直接，不使用营销化承诺。

#### Scenario: 空集合与读取失败
- **WHEN** Skill 列表为空或读取 Skill 列表失败
- **THEN** 空态说明尚无条目并给出上传入口；读取失败说明无法取得当前列表并提供重试，不声称条目不存在

#### Scenario: 保存与运行状态不同
- **WHEN** 运行时配置已保存，但 Core 返回运行时不可用
- **THEN** 页面分别说明“配置已保存”和“运行时暂不可用”，保留真实状态码供诊断，不宣称整体失败或已就绪

#### Scenario: 包安装结果尚未确定
- **WHEN** 浏览器上传结束、Core 已接受安装，或观察 Operation 的请求中断
- **THEN** 页面分别说明上传、接受或观察中断的已知事实，保留 Operation ID 和历史状态，提供继续查询入口，不宣称安装完成或自动重提

#### Scenario: 界面语言与原始数据
- **WHEN** 管理员在英文面板查看含中文资源名称、`AGENTS.md` 内容或 Core 返回的非英文错误消息
- **THEN** 导航、操作、提示、确认与无障碍名称仍为英文；用户内容和技术标识保持原值；非英文服务端消息不直接充当 UI 说明，管理员仍能看见英文原因或状态、下一步以及安全的诊断标识

#### Scenario: 字段错误与整体失败
- **WHEN** 表单同时有字段校验错误与一次读取或提交失败
- **THEN** 字段附近说明该字段的修正方式，section 内单独说明整体失败及下一步，错误码、字段和关联 ID 只作为辅助诊断，且不将未确认的服务端自然语言消息当作主说明

#### Scenario: 草稿、提交与未知结果
- **WHEN** 管理员编辑设置并提交，随后遇到请求中断或明确的校验失败
- **THEN** 界面区分未保存草稿、提交中、明确失败和结果未知；明确失败保留可修正草稿，结果未知提示先读取当前配置，不暗示已保存或自动重提

### Requirement: 容器层级与内容职责跨页面一致

**Identifier:** UIL-009

Serve 管理面板 SHALL 按容器角色而非路由名称决定内容布局：页面轨道承载标题、范围说明及一级 section；每个一级 section SHALL 对应一个可说明的管理目的和所属操作；表单及字段组 SHALL 在该 section 内承载输入、限制、字段错误与提交动作；列表行或表格行 SHALL 保持对象名称、当前状态及该对象动作的关联；详情 SHALL 先呈现可判断的摘要，再呈现可展开或局部滚动的原始配置、来源、错误标识及 Operation 技术内容。加载、空、失败、警告、提交中和未知结果 SHALL 显示在其所属的页面、section、字段或对象旁，不为状态切换额外创建不同宽度的一级卡片。页面级连接错误 SHALL 保留页面对象与恢复入口；字段错误 SHALL 在字段附近，整个 section 的读取或提交错误 SHALL 在对应 section 内，安全诊断标识 SHALL 位于主说明之后。上传进度及异步 Operation 状态 SHALL 与触发的表单或所查询的 Operation 同属一个上下文。

仓库级 UI 与产品语言 SHALL 为现有的顶栏、页面标题及说明、一级 section、摘要、表单、字段组、选择与排序行、列表及表格、详情、技术披露、反馈与操作区分别提供容器规则。后续若引入对话框、浮层或侧栏等新容器，变更 SHALL 先声明其对象、作用范围、宽度归属、焦点及窄屏规则，且不得改变现有页面轨道；现有浏览器原生确认框 SHALL 继续按既有目标与后果文案规则使用，不被当作可由 CSS 测量的页面卡片。

#### Scenario: 列表、表单与字段错误
- **WHEN** 用户页同时展示账号列表、创建表单及一个无效字段
- **THEN** 列表和表单各自占据同宽一级 section，列表行保持账号与操作关联，字段错误位于对应输入附近，创建结果位于该表单上下文内

#### Scenario: 技术详情与长内容
- **WHEN** 默认 Work、Package 或 Operation 详情展示长名称、公开配置或技术 JSON
- **THEN** 先能读取对象摘要及主要动作，再访问完整技术内容；换行或滚动发生在所属容器内，页面和一级 section 宽度不变

#### Scenario: 状态切换不改变容器位置
- **WHEN** 同一页面从加载变为空集合、读取失败、提交中或结果待核实
- **THEN** 对应状态与恢复入口仍出现在同一对象或 section 上下文内，页面标题与一级卡片两侧边界保持稳定，不出现孤立的不同宽度反馈卡片

#### Scenario: 后续新增容器
- **WHEN** 后续浏览器 UI 引入确认对话框、浮层或侧栏
- **THEN** 对应变更先按本 Spec 明确对象、内容职责、宽度与响应式、焦点和关闭或恢复方式，页面主轨道及已有一级 section 对齐规则继续成立

## ADDED Requirements

### Requirement: 在 Spec 中保留共享语义颜色基准

**Identifier:** UIL-011

Console 与 Desktop SHALL 沿用同一组浅色语义基准：页面背景 `#F5F8FC`、顶栏/次级表面 `#F8FBFF`、主表面 `#FFFFFF`、分组边界 `#DCE7F2`、控件边界 `#BAC9D8`、主要文字 `#1B2634`、辅助文字 `#526477`、交互强调 `#0969DA`、强调悬停 `#0759BA`、低强调背景 `#EAF3FF`、危险/错误 `#B42332` 和警告 `#8A5A00`。迁移 SHALL 保留这些已有基准，不通过删除文档引入另一套默认主题；未来调整通过对应 OpenSpec 变更表达。颜色 SHALL 与文字、可见焦点和可操作的反馈共同表达状态，不能成为状态的唯一依据。

#### Scenario: 文档迁移后新增浏览器页面
- **WHEN** 开发者在根 `docs/` 已移除的仓库中新增或调整浏览器页面
- **THEN** 能从本 Spec 得到共享语义颜色及适用范围，并按 UIL-002、UIL-004 与对应能力验证，不依赖被删除的说明文件

#### Scenario: 两端采用相同颜色角色
- **WHEN** Console 与 Desktop 同时呈现主要动作、错误和警告
- **THEN** 相同语义使用相同基准，状态仍由文字和必要操作明确表达，Serve 的布局限制不扩散到 Desktop

### Requirement: 在 Spec 中保留管理表单的内部对齐基准

**Identifier:** UIL-012

在 UIL-003 的统一页面轨道内，管理表单 SHALL 按所属容器和现行响应式规则对齐。在 1440px 参考视口下，任务页表单 SHALL 使用 156px 标签列、16px 列间距及占据剩余宽度的控件列，内部网格最多 712px；达到该宽度时控件列为 540px，SHALL NOT 对所有表单施加 520px 的统一控件上限。输入、选择器、文本区、文件选择、字段组、帮助、错误和提交动作 SHALL 共用所属表单的控件列边界。

其他管理容器 SHALL 保留各自现行网格，包括已有的 176px 标签列及最多 520px 控件列，不能把任务页的 156px 标签要求扩散到所有表单。响应式断点 SHALL 继续按所属容器调整列宽与动作缩进；空间不足和 360px 窄屏 SHALL 折为单列，帮助、错误和动作随单列对齐。登录单任务容器 SHALL 保留最大 420px 的例外。迁移 SHALL 保留已有布局和操作语义，通过校正规格表达完成归并，不以旧文档尺寸改动现行 UI。

#### Scenario: 迁移后核对管理表单
- **WHEN** 维护者在 1440px 参考视口检查达到 712px 内部宽度的任务页表单
- **THEN** 标签列为 156px、间距为 16px、控件列为 540px，帮助、错误和提交动作沿控件列对齐，不因旧文档的 520px 上限收窄当前表单

#### Scenario: 按容器保留内部网格
- **WHEN** 维护者比较任务页、其他管理容器和登录表单
- **THEN** 各自沿用现行容器规则，其他管理表单不被统一改成 156px 标签列或强制使用 176px 标签列，登录容器保持最大 420px 的例外

#### Scenario: 响应式表单折叠
- **WHEN** 维护者在现行响应式断点和 360px 视口检查管理表单
- **THEN** 列宽与动作缩进按所属容器规则变化，360px 下折为单列且帮助、错误和动作与输入对齐，主要操作仍可达

#### Scenario: 长技术内容与表单同页
- **WHEN** 管理页面同时展示表单、长 ID 或宽表格
- **THEN** 内容在所属容器内换行或滚动，不改变统一页面轨道、表单对齐或主要操作的可达性
