# Spec Delta

## MODIFIED Requirements

### Requirement: Session 与 Run 的观察可恢复且不重复提交

**Identifier:** DWUI-004

Desktop SHALL 提供 Session 创建、列表、读取与切换，提交消息、文本/工具事件、Run 详情和显式取消，落实 DUL-012。标题使用真实首消息摘要或创建时间/ID。一个 Work 活跃 Run 的限制 SHALL 在其他 Session 提交前后都明确反馈，保留草稿且不建立隐藏队列。取消以当前 Run ID 为目标，取消中不预告终态。

断线恢复 SHALL 按原 Run ID 和事件游标查询/观察，重复事件去重；游标过期 SHALL 查询结果和 Session 历史，不重发 prompt。旧 context 不兼容 SHALL 提供 New session 并保留草稿，不自动迁移。停止 Work 不新取历史，页面已有内容标为旧内容。所有观察 SHALL 在切换身份、对象或页面卸载时释放本地连接，不取消远端执行。

手动 Run 与由显式 Service 请求受理的自动 Run SHALL 共用真实 Session/Run 历史和观察能力。自动处理记录与已经受理的 Run SHALL 分开表达：待处理或等待状态不等于正在执行模型；自动请求不是手动消息的隐藏队列。每个 Run SHALL 展示实际模型及执行来源，Service 来源 SHALL 能定位请求、已核验的事件/证据和当前阶段。关闭观察不取消请求；Cancel run 取消当前 Run，若关联未完成请求则同时结束其后续自动续接；Cancel request 可直接取消待处理、执行中或等待中的请求。

当前用户 Chat 的输入区 SHALL 将独立 Cancel run 与新消息发送分成可辨的两个动作。已确认的可取消活动 Run SHALL 有不依赖非空草稿、模型选择或新消息有效性的独立停止入口；仅取消目标 Run，不提交新消息或消费草稿。当前用户 Chat 的模型发送 SHALL 根据本 Work 的真实活跃 Run 与独立能力确认，在原 Send 位置显示 Stop and send；目标快照绑定原 Core/账号、Work、Session、旧 Run、输入内容和原 submissionKey。用户点击或在该动作明确可见时按 Enter 才执行 CONV-CANCEL-SEND-001；空输入、未确认模型设置、非法图片或失效资源命令不得取消旧 Run。Shift+Enter、输入法组合和五个网页 slash 动作保持原行为；仅导航或编辑不请求取消。

Stop and send SHALL 可以取消同 Work 的任意来源旧 Run，取消与新提交由服务端协调，确认旧执行结束后才接受新 Run；不能把按钮操作拆成可能被后台抢槽的独立隐式发送。旧 Run 已终态且没有另一个活跃 Run时正常提交；出现新的不同活跃 Run 时保留输入并重新确认目标，不扩展取消授权。取消等待最多 5 秒；超时、明确拒绝或新受理前失败保留文字、图片和设置，超时后不得因旧 Run 稍后结束而自动发送。提交接受响应未知时保留原键并按 CONV-SUBMISSION-001 只读核对。

当前 Work 活跃 Run 的读取 SHALL 不切换当前 Session 或加载其他 Session 全部历史；支持能力未确认、Work 不可达或读取失败不得当作已确认空闲。未支持组合动作的旧 Agent SHALL 保留已有 Cancel run、普通 Send 和 busy 提示。已受理 Run 的执行与观察断线规则不变。

Chat 正文 SHALL 移除 Run History ID 列表，原 Session/Run 数据及实际模型、Thinking、来源仍在按需 Run 详情可读。历史详情 SHALL 绑定明确的原 Run，不覆盖当前活跃 Run 的观察对象，不取消或提交执行；错误、进行中与未知提交恢复仍在所属上下文可见。正常成功与已受理回执 SHALL 不再以常驻 Run 状态行或 Message accepted 卡片重复占用正文和输入区；失败、中断、部分输出及观察未确认的事实与恢复入口 SHALL 留在原轮次。

全 Work 活跃 Run 的投影 SHALL 只决定忙碌说明及明确的停止目标，不取代当前 Session 原 Run 的错误和观察恢复投影。当前 Chat 原错误、失败及未知反馈 SHALL 在其他来源占槽时继续可见；打开原 Run 详情或核对原状态 SHALL 不覆盖活动槽的观察对象、不改绑停止目标，也不提交执行。旧消息缺少可确认关联时保留原未知表达，不猜测另一个 Run 属于当前用户消息。

事件入口返回 410 后，Desktop SHALL 真正读取原 Run 和对应 Session；只有历史读取成功后才能提示历史已恢复。SHALL 停止向事件入口重发同一失效游标，不擅自用 0 重播。原 Run 仍活跃时 SHALL 展示历史恢复模式，以串行只读查询观察原 Run 和已保存历史；查询到终态后 SHALL 停止自动观察并呈现最终结果，已有输出不得重复追加。读取失败 SHALL 保留已知内容、Run ID 和可恢复提示；鉴权失效或对象不存在 SHALL 停止自动读取并进入对应恢复状态，不能发送新的 Run。

当前身份各 Work/Session 中未发送的非空文字或图片草稿 SHALL 纳入页面刷新、关闭和离开的未保存保护；浏览器支持且满足提示条件时请求原生离页确认，取消离开保留原草稿。不自动发送、上传或新建 Session，不承诺浏览器强制关闭、崩溃或不支持离页提示时能恢复。首版不新增跨关页草稿持久化；账号/Core 切换、注销和本地授权失效仍清理旧身份草稿及图片预览资源。可靠受理只消费本次提交快照，后续新编辑仍受保护。

Run详情入口 SHALL 绑定实际Work/runId及Session上下文，并跟随对应一轮消息/Activity或明确活动执行状态；没有runId的历史消息不推测绑定当前最近Run，同一Run不因多段消息重复展示详情。全Work业务请求与Session对话、单次Run SHALL 分层，Request与Run各自显示真实状态；等待请求可没有活跃Run，某次Run成功不能推导目标完成。请求列表/详情展示调整 SHALL 保持分页、原过滤、取消竞争、historical只读及Retry新请求语义。

Assistant消息正文 SHALL 支持GFM标题、强调、列表、链接、代码块及表格，历史与流式增量采用同一renderer；用户文字与工具输出保持原义。原始HTML不得执行，危险/相对链接不得导航本地授权页面，外链隔离opener，Markdown图片不自动读取外部资源。超出解析预算或解析失败时 SHALL 保留完整转义文字；表格和代码在消息内横向滚动，不撑开Chat或覆盖输入区。现有source入口、鉴权图片、Session/Run身份与阅读位置规则保持。

#### Scenario: 历史与新回复含表格或代码
- **WHEN** 打开已有assistant历史或接收增量Markdown表格、未闭合代码围栏
- **THEN** 正文安全解析或完整转义回退，表格/代码可局部滚动，危险HTML与URL不执行，用户/工具文字及原附件入口不改变

#### Scenario: 忙碌时保留输入
- **WHEN** 同一 Work 的另一 Session 正在执行而当前 Session 发送失败为 busy
- **THEN** 显示活动执行入口并保留草稿，不排队、不取消旧 Run

#### Scenario: 断线与游标过期
- **WHEN** 事件观察断开，恢复请求报告游标过期
- **THEN** 从原 Run 结果和 Session 历史恢复，只呈现一次已有输出，不发第二次消息

#### Scenario: 取消与成功竞争
- **WHEN** 用户取消时 Core 已经成功完成 Run
- **THEN** 最终显示 succeeded，不能以本地取消请求覆盖真实结果

#### Scenario: 等待请求不是活跃 Run
- **WHEN** Service 请求等待 Job 完成，而当前 Work 没有活跃 Run
- **THEN** 显示等待对象和最近确认时间，手动聊天可以正常受理，不将等待展示为模型持续执行

#### Scenario: 取消范围可辨
- **WHEN** 用户打开自动 Run 的详情
- **THEN** 能分别识别当前 Run 和来源请求的状态与取消影响，取消请求后不得再自动续接

#### Scenario: 当前 Work 的其他 Session 或 Service 占槽
- **WHEN** 当前用户 Session 有可发送草稿，真实活跃 Run 来自另一 Session 或 Service，且能力已确认
- **THEN** Send 位置提供 Stop and send 并明确旧执行来源，用户确认后在原用户 Session 接受一个新 Run，最多一个执行占槽，用户会话与草稿不被后台对话替换

#### Scenario: 无效新消息不影响旧执行
- **WHEN** 用户尝试用空输入、非法图片、未知命令或未确认模型执行 Stop and send
- **THEN** 保留内容并说明校验原因，旧 Run 不收到取消，没有新 Run

#### Scenario: 取消等待超时且旧 Run 随后结束
- **WHEN** 旧执行在取消请求后 5 秒仍未收尾，并在界面已收到超时后才结束
- **THEN** 显示取消等待超时与原状态核对，草稿保留，没有新消息自动提交，旧执行槽在实际停止前继续保留

#### Scenario: 目标变化和完成竞争
- **WHEN** 原目标 Run 先完成，或它完成后新的不同 Run 已占槽
- **THEN** 前者保留原结果并正常发送；后者保留草稿并更新忙碌目标，不取消新 Run、不自动发送

#### Scenario: 接受响应丢失与后续编辑
- **WHEN** Stop and send 的新 Run 已受理但响应丢失，或用户在等待期间继续编辑下一条内容
- **THEN** 按原 submissionKey 查询同一 Run且不重发，确认只消费已提交快照，后来的文字、图片和模型选择保持

#### Scenario: 原能力降级与历史详情
- **WHEN** Agent 未声明组合动作能力，或用户查看已完成 Run 的执行信息
- **THEN** 前者保留普通聊天与显式 Cancel run，不静默升级镜像；后者不显示正文 ID 列表，详情仍可读实际设置、来源和诊断，不替换当前执行观察对象

#### Scenario: 后台活动与当前 Chat 错误并存
- **WHEN** 当前 Session 有已确认失败或观察中断的原 Run，另一 Session 或 Service 随后占用活动槽
- **THEN** 原错误与按原 Run 核对的入口继续可见，忙碌来源及 Stop and send 指向另一个真实活跃 Run，草稿、Session 和原观察关联保持

#### Scenario: 410 后原 Run 已完成
- **WHEN** 事件入口返回 410，原 Run 查询确认 succeeded 且 Session 保存了最终回答
- **THEN** 实际读取 Session 并展示最终回答一次，停止自动读取，不重复 POST prompt 或请求失效事件游标

#### Scenario: 410 后原 Run 仍运行
- **WHEN** 事件入口返回 410，原 Run 先返回 running 后进入终态
- **THEN** 通过同一 Run 的只读状态和 Session 历史查询看到运行中及终态，事件入口不收到同一失效游标的无限重试，终态后查询停止

#### Scenario: 历史恢复失败或身份切换
- **WHEN** Session 读取失败、鉴权失效，或用户在历史恢复期间切换身份
- **THEN** 不显示虚假的恢复成功；读取失败保留已知内容和恢复入口，身份失效后停止旧观察且旧响应不写入新身份

#### Scenario: 文字或图片草稿触发离页保护
- **WHEN** 用户交互后在任一 Session 保留未发送文字或合法图片并尝试刷新页面
- **THEN** 支持的浏览器请求离页确认；取消后文本、图片和归属保持，没有 Run 或上传；只有全部草稿已消费/明确丢弃时不因聊天草稿阻止离开

#### Scenario: 旧身份草稿不会被离页保护保留到新身份
- **WHEN** 用户注销、切换账号/Core 或本地授权失效
- **THEN** 按原安全规则清理文字、图片和预览资源，不因离页保护留下可被新身份读取的内容

#### Scenario: 当前对话和其他来源的执行详情不混淆
- **WHEN** 用户查看当前Session历史Run，同时Work由其他Session/Service运行或存在等待请求
- **THEN** 各入口只打开精确原Run/Request，来源可辨，旧消息不绑定最新执行；关闭查看不停止Run或恢复等待目标

#### Scenario: 多次执行的请求仍以目标状态为准
- **WHEN** 请求关联多个Run，其中某次succeeded但目标waiting_result/waiting_apply/needs_attention
- **THEN** 原请求状态与必要下一步直接可见，执行、回复与证据按真实关联呈现，不虚构整体完成或重放mutation

#### Scenario: 无新草稿仍可停止
- **WHEN** 本 Work 有已确认可取消活动 Run，用户输入为空或新消息的模型／图片尚不满足发送条件
- **THEN** 独立停止仍可显式取消该原 Run；无 Run 提交，文字、图片和设置草稿保持，不能把模型发送限制错误地当成停止限制

#### Scenario: 独立停止和组合发送分别执行
- **WHEN** 用户有新草稿并分别选择独立停止或 Stop and send
- **THEN** 前者只发送原 Run 的取消请求；后者经过原新消息校验，按 CONV-CANCEL-SEND-001 一次提交协调取消与受理，不拆成客户端先取消再普通发送

### Requirement: Chat 按真实对话顺序合并历史与实时内容

Desktop SHALL 在同一 Session 内按可信历史顺序和已知 Run/消息身份合并分页历史、实时消息与工具活动。旧消息及其 Run 状态 SHALL 保留在所属轮次，不得因读取、合并或新消息受理而移到新轮次之后；无法确认归属或顺序的内容 SHALL 保留并明确未确认，不得按文字或时间猜测绑定。历史重读 SHALL 保留尚未在历史中确认的已显示输出，直到同一内容被完整替换或明确表明无法恢复，且不得重复显示。页面刷新、游标过期恢复及加载更早消息 SHALL 不改变真实顺序或隐式提交、取消 Run。

#### Scenario: 旧取消轮次与新的数字消息
- **WHEN** 已保存对话中旧 Run 为 cancelled，随后同一 Session 的“1”和“4”两次 Run 成功，且历史和实时消息混合加载
- **THEN** 旧取消状态随旧轮次显示在“1”和“4”之前，两次新 Run 各自保留成功结果并可在其详情核对，消息及正文不重复

#### Scenario: 历史不完整或读取失败
- **WHEN** 历史分页、Run 重读或游标过期恢复尚未覆盖已显示的实时正文，或读取失败
- **THEN** 保留已知正文与原 Run 归属并提示未确认，不用空结果覆盖，不猜测缺失内容

#### Scenario: 同文不同轮次
- **WHEN** 不同 Run 含相同用户或 Agent 文本、相同工具名称，历史分页以不同顺序返回
- **THEN** 按消息和工具的可确认身份合并，各轮次保持独立，不按文本、工具名或最近 Run 去重或绑定

#### Scenario: 连续发送后补读终态历史
- **WHEN** 同一 Session 连续完成多个 Run，终态补读按 Run 分别返回，或最近快照缓存发生淘汰
- **THEN** 通过同一冻结快照的有界 Session 页及必要已读轮次边界保持可靠顺序，已验证关系不被缓存淘汰遗忘，正常消息不误报顺序未确认；不自动遍历整份历史或提交业务动作

#### Scenario: 真正的历史异常按消息查看
- **WHEN** 部分正文、顺序或保存归属仍无法可靠确认
- **THEN** 原消息外显示可访问的状态图标，点击／键盘展开原消息的具体事实及只读重查入口；正文和 Activity 摘要不常驻技术警告，新草稿、展开及阅读位置保持

#### Scenario: 运行中恢复后终态包含多页新正文
- **WHEN** 原 Run 在运行中已做过历史恢复，之后保存的正文超过一页并进入取消、失败或中断终态，最终结果为空或不存在
- **THEN** 在本次冻结快照内继续沿该原 Run 的游标补齐可取得正文，不因首个页已缓存或旧快照曾读完而提前退出；正文保持一次、真实终态不变，不遍历整个 Session 或提交新的消息

### Requirement: 提交状态与 Agent 状态属于对应消息

Desktop SHALL 在用户提交时立即在原 Session 的对应用户消息位置展示提交快照。发送中 SHALL 以气泡外固定位置的低权重旋转图标表达，明确失败与结果未知分别使用可区分形状的失败图标与未确认图标；不常驻 Sending、发送失败等状态文案或 Message accepted 卡片。图标 SHALL 有本地化的可访问名称和可发现的悬停／聚焦说明，失败与未确认图标可点击／键盘展开原因及恢复动作；状态变化不改变气泡宽度、推移正文或裁切恢复弹层。可靠受理后移除发送图标并与原 Run 合并一次，不增加成功图标或重复消息。

明确未受理的失败 SHALL 提供用户显式触发的重试：使用原输入快照、所属 Session、原模型／Thinking 选择语义、图片、输入模式与上下文，重新校验当前准入；不得改用后续草稿或自动取消新的活动 Run。一次重试最多产生一个新受理，原消息保留为同一可追溯消息位置，失败尝试和新提交键有明确归属。结果未知 SHALL 仅按原键只读核对；未找到映射、读取失败或仍在受理期间保持未确认，不提供重发或以其他 Run 解除保护。恢复和受理只消费匹配的本次提交快照，不清空后续文字、图片或设置。

Agent 所属 Run 真实 accepted/running 时 SHALL 在原回复位置表达进行中。尚无正文时在该轮回复位置提供轻量等待图形；已有正文流式输出时，沿用既有全局三点并紧跟最后一段可读正文末尾，保持垂直居中，不另加“Agent 正在回复／准备回复”状态行。工具执行时由所属工具活动摘要承接该轮等待动效，不再叠加正文末尾与独立 Run 状态的相同提示。Markdown 表格、列表和代码等块末尾 SHALL 使用同一正文流内的安全末尾位置，不把动效插入代码内容、生成新的状态文案或破坏正文。

终态后移除等待动效。取消中、取消失败、断线未确认、执行失败、部分输出及终态 SHALL 按真实结果区分，并保留所属对象的恢复和详情；不得把已经受理后发生的 Run 失败改成“发送失败”。旧轮次状态不成为新轮次状态。中英文、窄屏、键盘、触摸及减少动态效果遵循既有 Desktop 规则。

#### Scenario: 发送受理与继续编辑
- **WHEN** 用户发送文字或图片并在等待受理期间编辑下一条草稿
- **THEN** 原消息旁只有发送图标；可靠受理后图标消失且只有一条对应消息，后续草稿保持，没有 Sending、Message accepted 或额外成功行

#### Scenario: 明确失败后重试
- **WHEN** 一次提交被明确拒绝，用户打开该消息的失败图标并选择重试，同时输入框已有不同的新草稿
- **THEN** 显示原因与可执行方向，重试针对原快照且最多一次受理；不消费新草稿、不追加重复用户气泡，不把同文的另一消息绑定为本次重试

#### Scenario: 结果未知
- **WHEN** 发送响应丢失，按原键检查未找到受理映射、读取失败或后来确认受理
- **THEN** 前两者保留未确认图标、原键和检查入口且不重发；确认受理时仅关联原 Run 并移除图标，不产生第二次模型提交

#### Scenario: Agent 生成和工具执行
- **WHEN** 当前 Run 等待回复、输出正文或执行工具
- **THEN** 每阶段在所属轮次只有一个等待提示；有正文时三点跟随正文末尾，工具执行时动效归工具摘要，终态后消失，没有新增回复状态文案

#### Scenario: 长 Markdown 与窄屏
- **WHEN** 正文以段落、列表、表格、代码块结束，或 360px 视口内用户打开消息状态说明
- **THEN** 正文和动效保持正确顺序与可读位置，弹层和其恢复动作不被聊天滚动区或输入框裁切，无整页横向溢出，静态状态不靠颜色独自表达

#### Scenario: 观察连接失效
- **WHEN** 已受理 Run 的观察断开但执行状态尚未确认
- **THEN** 保留消息和已有回复，在原轮次提供观察未确认及恢复；停止宣称正在生成的动效，不假称发送失败、取消或完成

#### Scenario: 旧尝试与身份切换
- **WHEN** 一条消息已重试或用户切换 Core／账号／Work／Session 后，旧受理或检查响应才返回
- **THEN** 响应只更新仍匹配的原尝试与对象，不覆盖新尝试、消费新草稿、改绑其他 Run 或把内容带入另一身份

### Requirement: 停止并发送使用停止图标并保留组合动作语义

输入区 SHALL 区分独立停止按钮与原主发送按钮：独立停止使用居中方块图标，可访问名称及悬停说明明确表示取消已确认的目标 Run；原主发送按钮在空闲时表达 Send，在已确认支持 Stop and send 且存在合法新输入及可取消目标时以含停止方块和发送含义的组合图标表达 Stop and send。两个动作的目的 SHALL 通过形状、完整提示及可访问名称区分，不能让一个无说明的方块同时承担两个动作。

用户点击主动作或在该主动作明确可用时按 Enter 才执行 CONV-CANCEL-SEND-001，不能仅取消或在本地等待后另发普通提交。独立停止不要求非空输入、不发新 Run，也不改变新草稿及模型／图片。Shift+Enter、输入法组合、重复按键、网页 slash 动作、未支持组合能力的旧客户端与旧 Agent 均遵循原准入和恢复规则。独立停止不因组合能力缺失而退化为不可用。

停止入口 SHALL 绑定用户看到的同 Work 确切活动 Run；其他 Session 或 Service 来源须可辨，若目标变化则重查并提示，不自动扩大取消授权。取消请求待确认或已处于 cancelling 时阻止重复取消，保留真实状态与必要核对入口；网络失败不显示“已停止”，已经成功的 Run 不改写为 cancelled。未知新提交期间不借原目标结束自动再发新消息。

#### Scenario: 活动 Run 中提交新消息
- **WHEN** 活动 Run 已确认且能力支持，用户输入合法消息并选择组合图标主动作
- **THEN** 动作名称明确为 Stop and send，服务端确认原目标收尾后受理新消息一次；失败、5 秒取消超时或接受未知保留原快照与核对保护

#### Scenario: 单独停止与继续编辑
- **WHEN** 用户空输入或有新草稿时选择独立停止
- **THEN** 只取消绑定 Run，取消中防重复；不新建 Run 或 Session、不消费任何新草稿，已输出正文保留并按真实终态表达

#### Scenario: 不可发送并不等于不可停止
- **WHEN** 模型选择未确认、图片尚不可发送、组合能力不支持或输入为空，但已确认原 Run 可以取消
- **THEN** 合法的独立停止仍可用，主发送动作按实际原因受限；发送准入不被反向用来阻塞已授权的取消

#### Scenario: 取消失败及目标竞争
- **WHEN** 取消请求失败、成功终态先提交，或所见 Run 被另一个 Run 取代
- **THEN** 显示原对象的失败／实际成功／目标变化，不假称已停止、不取消新出现的 Run，保留原正文与新草稿

## ADDED Requirements

### Requirement: Chat 一轮消息统一层级并保留阅读连续性

用户气泡 SHALL 按内容占宽、在右侧有界排列；Agent 正文、作者标识、工具活动与低权重详情 SHALL 统一左对齐及字阶，复用 Piwork 浅色令牌。只借鉴聊天气泡形态，不更改 Work 导航、Service 内部界面或其他模块主题。同一 Run 的消息、工具与详情按原身份和顺序组织，不按文字相似度合并轮次，也不把同一 Run 的作者与执行提示重复堆叠。

正常执行与成功 SHALL 不再以 Run running／Run succeeded 常驻状态行占用聊天正文，已受理消息不在 Composer 再铺回执。原 Run 的实际模型、Thinking、来源和诊断通过绑定精确对象的详情保持可查；异常、部分内容、历史顺序或保存归属未确认的事实仍在原轮次清楚表达，不能为简化界面隐藏。

流式更新、工具结果、展开／收起和历史补读 SHALL 保留同一 Session 的输入节点、草稿、选区与合法焦点；用户上翻或展开阅读时不强拉到底部。处于最新位置时新内容可继续跟随；离开最新位置后提供回到最新的轻量入口。新消息受理不得吞掉已显示正文或先前工具结果。

#### Scenario: 一轮连续对话
- **WHEN** 用户提交后经历受理、工具调用、正文输出及完成
- **THEN** 原消息保留，回复过程在同一轮内连续呈现，正常结束只留下正文、工具记录与低权重详情，没有多套常驻执行回执

#### Scenario: 上翻并展开工具
- **WHEN** 用户向上阅读、展开工具详情，期间追加正文、工具结果或更早历史
- **THEN** 可见锚点、手动展开、草稿与选区保持；不强制收起或抢滚动，回到最新只改变阅读位置且不提交业务动作

### Requirement: Chat 工具活动按真实调用分层展开

工具活动 SHALL 默认收起，单次调用可用真实工具名及已取得的公开对象信息形成摘要，多次活动摘要保留调用数、当前状态与失败数量。不得根据邻近正文、文件名猜测参数或假装取得原型示例中的文件。失败／结果未确认仍在摘要可辨；终态结果不被后来到达的开始事件降级。

点击或键盘展开 SHALL 显示真实工具身份、实际状态和已有公开结果预览，支持只读查看，不调用、重试或取消工具。可取得的原始内容放在进一步按需展开的区域；参数或结果未由公开协议提供时如实回退到可用工具名和结果状态，不新增读取私有历史或扩大接口暴露。结构化或不可读结果按既有安全预览与截断边界表达，不执行输出中的 HTML。

展开状态 SHALL 绑定所属 Work／Session／Run／工具身份，实时更新、历史合并和终态到达不清除用户展开或重建导致焦点丢失。工具顺序与正文交错保持；多个同时运行调用可分别有真实状态，但每轮主等待动效只在相应活动摘要中出现一次。

#### Scenario: 读取工具及结果到达
- **WHEN** 一个已确认工具开始，用户展开，随后工具结果或 Run 终态到达
- **THEN** 默认摘要可展开，原展开与焦点保持，已有结果更新而不重做工具执行，正文与工具原顺序保持

#### Scenario: 参数或结果不可取得
- **WHEN** 公开记录只有工具名、调用 ID 和有界结果，或结果尚未确认
- **THEN** 先呈现已有内容并说明实际限制，不伪造文件路径、原始参数、成功结果或额外读取私有数据

#### Scenario: 多工具与失败
- **WHEN** 同一轮中有多个工具，部分失败、部分仍运行，或跨历史页取得同一工具的开始和结果
- **THEN** 摘要保持数量与失败可辨，调用按身份合并一次，完成不被开始覆盖，失败结果无需展开也可发现
