# Design

## Context

动机与范围见 proposal.md。现行源码存在两条读取路径：新版由 `HistoryProjection` 接收带字节坐标的历史页；旧版由 `mergeLegacyMessages` 合并完整 SDK 历史。旧 Agent 的 `history-capabilities` 返回 501、聊天能力版本为 1，是本次实际触发条件。原项目数据固定的 Agent 不会因为替换 Core 可执行文件而自动升级。

已确认的正常发送链路如下：

```text
accepted input --> Run-user -----------+
event stream ---> Run-text-sequence ---+--> legacy merge --> duplicate copies
saved SDK ------> entry-block ---------+
```

`acceptSubmissionMessage` 固定用户气泡为 `Run-user`；实时正文在 `resumeRun` 中使用首个事件序号。旧历史的文本块却使用 SDK `blockId`，只有图片用户消息已使用受理身份。兼容合并只匹配既有 ID，不匹配的实时消息被保留并标为未确认；普通的成功发送也因此出现两份。现有测试有意保留“相同文字、不同身份且没有对应证据”的两份数据，不能直接删掉该保护，而应增加正常链路的身份与覆盖证据。

一次只读回放确认：15 条 SDK 源记录去掉 system 并归并工具后投影为 13 条；回放最新已结束 Run 的已有事件，再补读同一历史后得到 15 条。用户消息与最终回复分别各多一份。该事实不表示历史数据库存在重复提交。

## Goals / Non-Goals

**Goals:**

- 区分逻辑消息身份与传输来源 ID，使同一输出从实时流转换到保存历史时连续、唯一。
- 让正常发送结束、重新读取、断线恢复共用同一规则；匹配范围限定于当前 Core 身份、Work、Session、Run。
- 对确有证据的覆盖归并，对未确认的独立消息或输出保留原事实；保持取消/失败正文和工具交错顺序。
- 合成回放覆盖原错误形状；部署时保留原账号、模型选择、SDK 历史和 Session。

**Non-Goals:**

- 不改变发送幂等、取消语义、公开协议版本、history schema 7 或 SDK 磁盘格式。
- 不引入文本相似度去重、全会话扫描、自动重发、自动升级所有 Work 或新的界面状态体系。
- 本轮不处理 MicroVM、Windows 制品和启动性能。

## Decisions

### 1. 只在可证明的作用域内建立来源别名

来源映射是当前页面的临时读模型，不写回 SDK。用户输入使用已受理的 Run 身份；同一 SDK 用户消息的多个文本/图片块先还原为一个输入。仅在已确认的唯一受理输入关联上使用 `Run-user`，多个无法区分的独立 SDK 用户消息不得按角色强并。

Agent 正文不以“同一 Run 的所有 assistant 内容”为一个对象。实时接收记录事件起点、是否从 Run 起点完整观察以及真实工具调用边界；SDK 来源保留 entry/block 身份和原顺序。只有同一 Run 内的起点、工具调用 ID 和有序字节覆盖可以证明对应时，才建立实时区间到 SDK 块的别名。多个 SDK 块可覆盖同一实时输出，但独立 SDK 消息及工具前后的合法同文不能因此消失。

替代方案：仅按字符串相等去重会吞掉合法重复表达；按角色整轮替换会丢失工具前正文和失败尾部；仅换新 Agent 会留下兼容分支缺陷。这些方案均不采用。

### 2. 保存来源与显示投影分离，按覆盖范围接替

在旧协议的局部读模型中保留尚未被确认覆盖的实时源及必要坐标。保存历史覆盖已读实时字节时，从显示投影移除该实时副本；只覆盖前缀时保留一次未覆盖尾部，后续增量仍追加到原始实时源，不追加到已经裁剪的显示片段。完整覆盖后释放不再需要的实时正文缓存和别名，避免重复读取反复生成尾部对象。

无覆盖证据、字节冲突或 SDK 结构不一致时，保持现有保护：不覆盖已知输出，不猜测关联；真实未确认事实使用现有消息外图标和只读详情。已确认的正常对应不能再以“ID 不同”为由把副本当异常保留。

`HistoryProjection` 的范围覆盖规则和 Agent `session-history.ts` 按工具边界逐字节核验的逻辑作为实现依据。优先复用可在浏览器中运行的纯范围处理逻辑，不把 Node/SQLite/文件系统依赖带入工作台。新分页路径继续使用服务端既有坐标，不退回旧整份读取。

### 3. 所有合并入口使用同一读模型

`legacy-history-projection.ts` 封装 Session 局部的旧来源规范化、受验证的别名和覆盖投影，复用 `chat-projection.ts` 的 SDK 解析与保守合并；`models.ts` 仅增加必要的临时来源信息；`adapter.ts` 在受理、实时事件、完整历史读取及游标恢复处传入同一上下文。`loadLegacySession` 与 `recoverRunHistory` 不再分别猜测终态身份。显式终态结果只对应同一 Run 最后一个纯文本 SDK 答案，不能吸收工具前的同文。

作用域包含页面身份代次与 Work/Session/Run；已有 AbortController 和 epoch 检查继续拒绝晚结果。切换身份、删除对象或停止观察时清理对应临时来源；重开页面可只读重建，不能靠持久化浏览器缓存才能不重复。更新使用稳定逻辑键，保留提交状态、输入草稿、Activity 展开和阅读锚点。

### 4. 修复兼容行为后，再显式升级报告中的 Work

先在旧能力夹具验证修复，防止升级掩盖错误；再构建包含修复资源和匹配 Agent/helper 的本地候选。通过现有镜像选择、配置保存和受管 Apply 仅更新指定 Work 的 Agent，沿用现有迁移备份、初始化与回滚；不直接改业务数据库、密码、模型凭据或 SDK 文件。原项目的运行数据目录和 admin 身份保留。

升级开始前确认目标 Work 没有活动 Run；有活动任务时保持运行，先完成可独立进行的构建与验证。成功后重新协商实际能力并只读打开原 Session。默认不向真实模型发送验收提示；若不能仅靠旧历史核验新发送，使用合成 Work 完成发送回归，并明确区分已测事实。

## Risks / Trade-offs

- [无事件起点或旧事件已过期，无法证明正文对应] → 保留已有保护和未确认状态，只归并已验证区间；不把相同文字提升为身份，也不承诺恢复旧版从未保存的内容。
- [工具并发、内容块拆分或同文造成错误匹配] → 使用真实调用 ID、原顺序和覆盖范围；工具开始/结果分别到达不改变正文边界，保留独立 SDK 消息。
- [显示裁剪后的尾部被当作流式源继续追加] → 保存实时源与显示投影分离，回归多次“增量—补读—增量”及最终完整覆盖。
- [局部读模型留下跨身份缓存或持有多份长正文] → 跟随现有身份生命周期清理，仅保存可见且未覆盖来源，确认后释放；复用既有预算，不扩大旧整份读取范围。
- [生产数据升级失败] → 只走既有受管升级并保留备份，按原流程恢复；不以覆盖真实目录、改密码或新建 Session 收尾。

## Migration Plan

1. 用合成输入/事件/SDK 历史固定旧协议重复回归；覆盖正确身份的情况和仍缺证据的情况。
2. 实现读模型与所有入口衔接，执行相关投影、历史和浏览器检查，保留新版分页路径回归。
3. 构建嵌入新资源的 Linux Core/CLI，核对实际源码身份和本地镜像身份；更换当前项目的 Core 进程，保持账号及数据目录。
4. 在空闲窗口对报告中的指定 Work 执行一次受管 Agent 升级，确认原 Session、Run、SDK 文件和模型选择保留，并重新协商能力。
5. 在原 Session 只读检查历史顺序与单份显示；汇总必要结果到 tasks 或所属验收附件。若升级或核验失败，按既有恢复流程处理并保留未完成项。
