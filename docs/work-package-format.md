# Portable Work package v1

A `.work` file is a complete cold snapshot of the product's durable Work boundary. Users do not author its manifest: Core creates it from a stopped Work, and both offline inspect and recipient Core verify it before use. The MIME type is `application/vnd.piwork.work-package`.

## Framing and integrity

The bytes are, in order: the eight ASCII bytes `PIWORK1\n`, an unsigned 64-bit big-endian manifest length, that many UTF-8 JSON bytes, then every raw blob in `manifest.blobs` order, each with its declared size. There is no blob header, compression, or trailing data. The package SHA-256 covers all framing bytes; each blob also has a SHA-256 digest. The manifest is strict JSON: duplicate keys, unknown schema fields, unsafe integers, malformed UTF-8, dangling references, and unsupported versions fail validation. Blobs are uniquely listed in digest order, and a reused digest carries the union of its declared kinds.

The manifest describes `formatVersion: 1`, `snapshotKind: "cold-full"`, source name and creation time, Linux/platform compatibility with `piPackageContract: 1`, active and desired context keys, all context and service revisions, persistent quota reservations, the two managed volume trees and their service references, fixed container images, model/secret binding requirements, `piPackageArtifacts`, and control-history and source-identity-map blobs. Every context carries required package selections and `packageBindings`, including empty arrays. Logical keys are relationships inside the package, not transferable platform IDs. History request/result/error JSON strings and user file bytes remain unchanged. The recipient assigns new Work, context, service, Operation, volume, network, and TLS identities; it preserves local Session/Run IDs within the newly isolated Work database.

Each volume, retained Skill directory, and Pi package artifact is represented by a tree blob. Entries encode POSIX filename bytes as base64 path segments and retain file data, empty directories, symlinks, hard links, uid/gid, mode, and nanosecond mtime. A Pi package artifact records its name, version, content and tree digests, prepared environment, safe provenance, and resource inventory. Bindings refer to artifact keys so multiple historical versions of one name can coexist; shared bytes may deduplicate without escaping logical restore limits. The separate `agent-private` and `workspace` trees preserve private-volume files hidden beneath the workspace mount. Unsupported special files or nonempty portable xattrs/ACLs cause the whole export to fail rather than disappear. The host-assigned `security.selinux` label is excluded from package metadata; restore retains the target host's label, while user xattrs, ACLs and file capabilities remain unsupported. The package contains the selected image config and uncompressed layers by immutable digest, not a mutable registry tag. Import reconstructs a tagless verified image archive and never executes package code during validation.

The SELinux exception matches only the exact attribute name, never the `security.*` namespace. Other attributes remain an error even when a SELinux label is also present. Attribute enumeration errors fail as unreadable storage. The same rule applies to owned context and package trees; it does not relax their existing link restrictions or permit restoring into a nonempty target. Label preservation is a tree-processing guarantee after normal runtime mount preparation: Docker may normalize a managed volume's private MCS label to shared `s0` under host policy, and the snapshot code does not prevent that behavior. No V1 field or format version changes are needed. Core and the snapshot helper must both include this fix. See the [SELinux acceptance procedure](selinux-snapshot-acceptance.md) for real Enforcing-host verification; changing to permissive mode does not remove file labels.

V1 limits are 100 GiB package bytes and 100 GiB logical restored bytes, 64 MiB for each JSON metadata blob, 256 MiB total metadata, one million tree entries, 4096 bytes per path, and depth 128. Reused blobs do not bypass the logical restore limit. A valid hash proves byte integrity, not that the sender or embedded code is trustworthy. Inspect neither opens the embedded SQLite database nor installs the Work; recipient Core validates history in its isolated helper before the package becomes importable.

## What is and is not copied

The portable boundary includes the Work's two managed volumes, Work-owned contexts, Skills and complete Pi package artifacts with prepared runtime dependencies, AGENTS.md, configuration and service revisions, desired resource reservations and volume references (including disabled/tombstoned leftovers), terminal control history, private conversation history, and fixed image content. Active, desired, historical, disabled, and removed-but-active package bindings are retained. No user-content filter is applied, so `.env`, source code, databases, dependencies, and user-stored credentials travel intact.

The boundary does not include the Docker container's temporary layer, anonymous volumes, tmpfs, live processes, external services, global users/catalog/secrets, or platform-managed credentials. Import requires the target Core to have an enabled matching model and a readable credential; it selects that binding automatically. The imported Work remains stopped and creates its runtime network and certificates only on explicit start. Import restores package bytes from the archive without consulting Core defaults/catalog or rerunning npm, Git, or package code; subsequent Work package operations use the recipient Core only when explicitly requested. The V1 schema requires the Pi package fields even when empty, and older V1 files without them are rejected. V1 is Linux and protocol/layout-specific; a package is not a generic backup of its host.

## Native implementation compatibility

The native implementation retains the exact V1 envelope, manifest, tree encoding and blob digests. It recognizes exact managed history schema 4 and schema 5 with Memory schema 1. The shared framing and static validation live in `internal/workpackage`, `internal/snapshottree`, `internal/imagestatic`, and `internal/workhistory`; the separate Go helper performs mounted-volume capture/restore and history reconstruction. SDK JSONL and user file bytes remain opaque. AGENTS.md is a file blob, not JSON metadata, and is restored byte-for-byte within the existing context bounds.

For schema 5, the original private volume contains both `work.sqlite` and independent `memory.sqlite`. Export retains Memory versions, selected entry IDs and original request/Evidence references. Import assigns a new Work and Memory store identity while preserving local versions, entry IDs and text. Old requests and candidates remain historical; importing them does not start tasks or publish candidates. Each copy has its own Memory authority. The workspace remains the second volume; formatVersion 1 and storageLayout 2 are unchanged.

Export requires a stopped Work. Unrecovered joint journals return `SNAPSHOT_HISTORY_BUSY`: complete recovery through the original Work runtime/storage path, stop the Work, then retry the existing Export command. Import preserves the captured runtime image and does not upgrade old history. A schema-4 Work upgrades only through explicit configuration Apply to a compatible new harness, with a saved history backup and initialization authorization. After successful upgrade, applying a schema-4-only image is rejected before replacement.

The recorded image must itself provide the supported native platform helper capabilities and the retained Node/Pi runtime. Static inspection handles links and layer whiteouts and never runs an image to infer compatibility. Only-TS helper images are rejected without substituting an image or adding a V1 field. Offline byte integrity and recipient installation validation remain separate: the Core still verifies target model credentials, external MCP requirements, quota, name availability and platform constraints before publishing a stopped Work.

Accepted Work exports and Work-scoped Pi package jobs retain Work IDs as idempotency resource IDs. Snapshot IDs and Operation IDs stay in their durable job records and public receipts. Imported history maps only platform-owned references; source URL text, database values, raw archived request/result strings, and package contents are not rewritten. See [native snapshot flow](work-snapshot.md#native-go-core-implementation) and [acceptance evidence](go-migration-acceptance.md).


Current history is schema 4 with thirteen fixed tables. The native verifier checks feedback, candidate, experience and SDK tool/input/check relationships without executing uploaded SQL. Rebuild changes only declared Work/context references and declared control Operation IDs. SDK events, tool inputs, user payloads and business files stay byte-identical; imported requests/events are historical and cannot schedule, cancel or retry original effects. Private helper input contains safe recipient model descriptions and the declared Operation map, never API keys. Explicit Session preferences bind only to a unique enabled recipient provider/model/normalized endpoint match; zero or multiple matches stay unavailable. Imported Service instances get fresh private identity; preserved source outbox records cannot claim the new origin.

Upload verification streams and hashes every archive blob, then reads validated archive sections directly for package and image checks. Only the managed SQLite files are materialized for isolated history inspection and are removed afterward. The helper does not duplicate image blobs into its spool, so an archive larger than the helper's memory limit can also be checked when the spool resides on tmpfs.
