# FastAPI + React Web application

This editable application uses the fixed `piwork-web-base` environment: Python 3.13, FastAPI, React, TypeScript, Vite and SQLite. The image is a reusable environment, not a business application. Its maintenance source is `deploy/images/web-base/` in the Piwork repository; see the package's `references/web-base.json` for the published fixed reference.

Read this template SPEC.md, then invoke the `initialize.mjs` beside the loaded deployment Skill through authorized Agent bash: `node <loaded-skill-directory>/initialize.mjs --template web-app --name <service-name>`. It creates `apps/<service-name>` exclusively, writes its Spec first and copies a writable template preserving executable bits. Every existing target is refused before any Spec/source/registration write. Read and adapt the new Spec before implementing business changes; maintain existing applications by reading and editing their actual files, never by copying the template again. An initialization failure must not continue to Service creation or restart. Source/locks/caches/builds stay in the application directory; business data is `data/<service-name>`, selected from the current injected Service identity. Register `.pi/services/<service-name>.json` with contractVersion 1, the actual serviceName, apiPortName `web`, and mode `pi-managed`.

Create the Service with an explicit workspace read/write grant, `workingDirectory=/var/data/workspace/apps/<service-name>`, command `/usr/local/bin/piwork-web`, args `["run"]`, the `web` TCP port 8080 and HTTP `/health` readiness. Check the actual deployment context for CPU/counts. Service memory is unlimited. The backend reads identity/CA only from `/etc/piwork/interaction`; browser code never receives the token.

`piwork-web prepare`, `check`, `build`, `serve` and `run` provide offline preparation, isolated backend/frontend checks, a checked frontend build, and single-port serving. `piwork-web dev` explicitly enables React Fast Refresh and backend reload. The application copy and its dependencies are writable; image tools remain fixed. Standard dependencies are offline; additional locked dependencies require retained wheels/cache or a derived image.

After editing, the Agent runs the required checks/build and updates/restarts the existing Service, observes its original Operation and verifies the running codeVersion and business output. The page detects ready versions automatically, reloads a changed frontend once, re-reads data after backend changes, and restores supported drafts/path. Users do not need to refresh. Failed builds do not publish a ready version; this does not automatically Apply brain/Work configuration.

The sample UI and Agent share Todos/review/export logic, idempotent Actions with expectedStateVersion, original asynchronous Jobs and transactional outbox. Explicit feedback starts a Pi request; ordinary facts do not. Imported historical events/Jobs do not replay. Workstation's initial omitted-completed-review configuration is a deliberate repair fixture; the general Web starter begins with completed items included. These sample business objects can be replaced with the requested domain.

The real sqlite3 CLI exists in both base and Agent. AI's bash runs in Agent and can inspect authorized workspace databases directly; ordinary business mutations still use the named Action/Query contract. No host sqlite3, Python, Node, Docker socket or host port is required.
