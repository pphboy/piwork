# Develop a persistent Service

For an operation on an existing Service, discover its capabilities, perform the named Query / Action, verify the actual result and return it. Do not edit code, create a Spec or start development tests for ordinary operations.

For construction or a code/configuration change:

1. Call `work-services__deployment_context`. Read [deployment request shapes](reference.md) and [the Service contract](../../references/service-contract.md). For a new Web application with no explicit stack, read [the fixed Web base identity](../../references/web-base.json) and use Python + NiceGUI + SQLite with [the Web starter](../../templates/web-app/README.md). Use a published fixed tag@digest; a missing/unpublished identity is a real environment failure, not permission to invent a tag. Local development or acceptance may explicitly select a verified prebuilt image; do not mistake a candidate tag or an old FastAPI image for a published NiceGUI environment. Respect explicit stacks, existing applications and third-party software. Use the actual Work resources and any appropriate language; [the Python protocol helper](../../templates/workstation/piwork_protocol.py) and workstation example are optional.
2. Before implementation, maintain `apps/<service-name>/SPEC.md`: Intent, Objects, State, Business Flow, Agent-operable Capabilities, Implementation Map and Acceptance Criteria. Keep it short. For an existing Service, read the current Spec and relevant code, update only affected sections, and retain concrete file/function coordinates. If its Spec is absent, derive the necessary current design from real code before changing it. Do this automatically without intermediate user Spec/Plan/Eval approvals.
3. Keep source/configuration and exact extra-dependency locks/offline materials in `/var/data/workspace/apps/<service-name>` and business data in `/var/data/workspace/data/<service-name>`. Keep a code/configuration checkpoint and an actual codeVersion. Do not rely on /tmp, the container layer or runtime downloads for persistence.
4. Implement the core business logic once for both UI and Agent. Provide the existing capabilities, Queries, idempotent Actions with expectedStateVersion, Action/Job result access, meaningful checks and transactional outbox. Register `.pi/services/<service-name>.json`. Third-party code remains external and uses actual lifecycle/endpoints/log observations.
5. Use an existing runtime image, fixed dependencies, 0.0.0.0 binding, declared API port and readiness probe. With NiceGUI base, set Service command `/usr/local/bin/piwork-web` and args `["run", "--app", "/var/data/workspace/apps/<service-name>"]`. Standard dependencies are already installed; the command performs missing/mismatched Python checks before serving port 8080 with `/health`, and identical input reuses passed checks. No npm or separate frontend build is needed. The command runs in Service, not Agent bash. Application Services have unlimited memory; do not treat deprecated memory budget fields as available Service memory. Keep CPU and count admission within the actual deployment context. Create/update the stable Service with a stable mutation key and expected definition version. Observe the original Operation, actual readiness and safe failure logs. No Docker build, host mount/port, privilege or Docker socket is required.
6. After edits, complete the relevant Python/application checks and stable Service update/restart yourself; observe the original Operation and actually loaded codeVersion before reporting delivery. Do not leave deployment, restart or browser refresh to the user. The standard NiceGUI page checks `/api/runtime-version`, adopts the actually ready Python page/environment and re-reads business state; drafts/path are restored by the application. Do not force-refresh the Desktop shell or unrelated/third-party frames. Run or update the existing tests for the affected Acceptance Criteria. Inspect actual exit/result output; retain the command, changed files and meaningful output in the existing SDK history/Files. Query the running Service and verify affected business results with Evidence. Process readiness, file creation and test declarations alone do not prove completion.
7. Use the original Action/Job identities and waiting/recovery rules in the Reference. Preserve unknown effects and business data. A code/configuration restore does not undo business transactions. Ordinary facts do not start Agent goals; only the Service's declared explicit feedback does.
8. If tests or business checks fail, attempt a bounded minimal repair under the existing Run/request budgets. Preserve failed results, original acceptance criteria and code recovery basis. If unresolved, report what changed and what remains unverified; do not claim Verified or publish failed learning.
9. Report changed files/features, current Spec coordinates, actual deployment, checks and Evidence through the existing Chat/Run/Service/Files/CLI results. Stage reusable verified knowledge in independent Work Memory when useful. Do not create a separate ledger, evaluation engine or task scheduler.

For NiceGUI page changes, maintain `page-files.json` and the Spec implementation map when introducing, splitting or removing page helper modules or local browser resources. The `files` array adds app-relative regular files to the default page inputs (`app.py`, `ui.py`, `page-client.js`, `style.css` when present). Do not list independent business modules, data, caches or dependency environments. Invalid, missing, escaping or symbolic inputs fail checks/startup; existing apps without a manifest retain the default set. Verify that an actual listed helper/resource change updates frontendVersion, while a business-only change preserves it.

The Service backend reads its injected interaction identity and CA; keep tokens out of browser JavaScript, environment, Work source and exports. Record only safe pathname/business facts, and expose own-request receipts through the backend as specified in the Reference.

For a new application, invoke `node <loaded-skill-directory>/initialize.mjs --template web-app --name <service-name>` through authorized Agent bash; resolve the script next to this loaded Skill. Use `--template workstation` for that example. The initializer rejects every existing target before Spec/source/registration writes, creates the necessary Spec first, preserves executable bits and makes the separate copy writable. Read and adapt the initialized Spec before implementing requested business code. A failed initialization ends this deployment attempt; do not continue create/update/restart or treat an old idempotent receipt as success. For an existing application, read its actual Spec/source and make targeted edits instead of reinitializing. Never modify the frozen mount. Formal Brain software maintenance follows the Reference's existing Package update path; Memory changes never enter it.


The Web base and Agent image both provide the real `sqlite3` CLI. SDK bash runs in Agent, so a Service-only binary is not evidence that Agent can execute it. Use existing authorized bash for workspace data development/diagnosis, prefer read-only queries for inspection, and keep ordinary business mutations on the named Action/Query contract. Do not edit platform-managed Core/history/Memory databases with SQL. If an old captured image lacks the command or bash is denied, report the actual limitation; do not install tools at runtime or bypass policy.

The image maintenance source is `deploy/images/web-base/` in the Piwork repository. Templates and this reference are consumers of its fixed environment, not an image build source inside the Work. Build/validate/publish a new environment from that repository, then select compatible versions through the normal mechanisms.


For additional Python packages, write only exact extra pins (or app-local wheels) to `requirements.in`. Use the existing Service update/start command with `run --install-deps` to acquire compatible missing packages explicitly. Agent bash has no Python/pip; do not use Docker exec/build or modify the read-only image. The installer retains `requirements.lock`, exact wheels and a versioned `.deps/` environment, inherits fixed standard packages, and rejects conflicts. Inspect the original Operation, safe logs, checks and actual application use; failure preserves the previous valid environment and data. Matching restart/import is offline; a missing or relocated environment is rebuilt from retained materials. Keep temporary/cache/HOME writes within the granted workspace. System-library or base-package changes require a separately prepared derived image.
