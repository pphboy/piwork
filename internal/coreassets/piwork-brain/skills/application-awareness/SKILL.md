# Piwork Application — Product & UI/UX Awareness

你正在 Work 工作空间中构建一个 Piwork 应用（Service）。一个 Work 可以包含多个 Service；应用应该真实、可用、可持续迭代，用户和 AI 都可能操作它。

在创建应用、开发功能或修改交互时读取本 Skill，并在当前实现中自然运用这些认知。当前上下文已有同一有效包的正文时直接复用，无需每次工具调用重新读取。仅修改后台能力时采用相关原则，不主动增加无关 UI。

使用 NiceGUI 创建/修改页面或排查页面异常时，按需读取本 Skill 旁的 [NiceGUI 指导](references/nicegui.md)，相对路径以当前 SDK 发现的冻结 Skill 目录解析。其他技术栈和普通业务操作无需读取该专项资料；同一有效上下文已有内容时复用。

### 1. Product：以用户任务为中心

- 理解应用要解决什么问题、用户主要完成什么任务。
- 优先实现最短、完整、可用的核心工作流。
- 不主动增加无关功能、复杂配置或过度抽象。
- 以实际使用体验判断功能是否完成，而不只是代码能否运行。

### 2. UI：简洁、清晰、一致

- 使用常见、成熟的 UI 布局与组件，保持基本的视觉一致性。
- 让重要信息、主要操作和当前状态容易被发现。
- 合理组织信息层级、间距、对齐和组件结构。
- 避免凌乱、拥挤、难以理解的界面，也避免不必要的视觉装饰。
- 不追求精美设计、品牌包装、复杂动画或定制设计系统。

托管浏览器入口带动态 Service 路径；自定义资源与 fetch 使用模板 URL helper，框架内置链接不重复加前缀，具体方式见 references/nicegui.md。不要把 Core 端口或固定 Work ID 写进浏览器源码。

应用自定义 CSS 类使用业务前缀，并尽量限定在应用根容器内。避免定义可能与框架冲突的全局 `.column`、`.row`、`.card` 等样式；有意调整框架组件也要限定范围并核对效果，不能误改其内部布局容器。

### 3. UX：操作自然，反馈明确

- 用户应该容易理解当前状态、可以执行的操作及操作结果。
- 交互尽量直接，减少不必要的步骤和确认。
- 根据实际需要处理加载、空状态、成功、失败等反馈。
- 遵循用户熟悉的交互习惯，不为了创新而创新。

### 4. Reactivity：状态自动更新

Piwork 是用户与 Agent 共同操作的工作空间。

- 用户操作或 Agent 修改 Service 数据后，UI 应自动反映最新状态。
- 不应要求用户手动刷新页面才能看到正常的数据变化。
- 根据现有技术栈选择简单可靠的状态同步方式。
- 不为自刷新引入没有必要的复杂实时架构。

UI 与 Agent 复用同一业务逻辑和权威状态。业务数据同步与代码版本自动采用分别验证；不要把新版页面已加载当作数据最新的证据。复用应用现有的简单查询、状态版本或订阅机制，不硬编码所有应用的同步周期。正常更新保留无关未提交输入、表单、焦点和当前操作；查询失败时按实际需要提示失败或陈旧状态，不把旧内容冒充最新。不为普通数据变化重部署、重启 Service 或发起新 Agent 目标。

### 5. Engineering Judgment：避免过度设计

以上原则是默认判断依据，而不是必须逐项执行的检查清单。

- 优先使用现有技术栈和成熟组件。
- UI/UX 应服务于功能交付，而不是阻碍交付。
- 不为了细微的视觉差异反复返工。
- 只有影响可理解性、可操作性或正确性的设计问题，才需要优先解决。

**完成标准：功能可用、操作直观、状态正确、界面整洁。达到即可交付，后续根据真实使用反馈迭代。**

对受影响的页面，有实际可用且获准的浏览器能力时，通过用户真正使用的 Desktop Service 入口确认内容可见、主要操作可用、状态自动更新。Service Ready、HTTP 200、业务接口通过或截图文件存在只能证明部分能力，不能替代页面验证。平台测试能使用 Playwright 不代表当前 Work 有浏览器工具或入口授权；能力缺失、入口不可达或授权不足时分别报告后端已确认结果与“页面未验证”及原因，不宣称完整 UI 交付，不擅自安装浏览器、扩大权限或获取用户凭据。

页面空白或不可操作时，先按实际现象检查资源、浏览器错误、连接、DOM、遮罩和样式证据。证据不足就说明原因未知，不直接归因为架构不兼容或更换技术栈；针对已证实原因修复后，从原用户入口复验。仅检查受影响页面的基本可用性，不新增视觉评分或全页面巡检。

将这些判断融入原任务，不增加独立设计阶段、设计报告、五项 Spec 章节、逐项审批、视觉评分、固定截图审核或额外 Agent/模型 Run。小改动只维护受影响的已有设计和验证，不顺带重做整个应用。用户明确提出的视觉目标仍按原范围实施；默认取舍不能取消用户要求，也不能跳过必要的功能检查、部署生效或实际业务验证。

普通 Query/Action、仅启停 Service、部署未改造的第三方镜像不进入此开发流程，不因这些认知自动改造既有应用。持久 Service 的必要 Spec、契约、环境、部署与验证继续由平级的 deploy-work-service Skill 承担；本 Skill 不复制该流程，不触发 Package/Work 自动 Apply，也不要求额外 Memory 步骤。
